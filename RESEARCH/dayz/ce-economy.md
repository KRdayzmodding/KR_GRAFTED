# Central Economy DayZ: карта подсистемы и путь к живому reload экономики

Разбор снят с **DayZServer_x64 1.30.164200.56 (retail)**. Выборочно перепроверено
автором graft на **1.30.164078.38**: парсеры из первой версии карты, зона спавна
(SpawnRandomLoot — тот же размер 0x10d0), формула респавна, lookup-пролог.
**Сдвиг между сборками не постоянный**: +0x98d0 у парсеров, +0x96c0 в зоне спавна,
около +0x9960 у `[CE][Hive] Loading core data` — адреса нельзя переносить из
сборки в сборку одним сдвигом, каждая находка перепроверяется паттерном.

Как читать пометки: `(статика)` — офлайн-разбор образа; `(живой замер)` —
поведение на работающем сервере 1.30.164200 (модовый, CF/RaG/Terje); `две сборки`
— сверено и на 164200, и на 164078. Адреса — VA при базе из заголовка
(0x140000000); для рантайма вычесть базу процесса.

Перепроверка после патча игры: `py -3.12 RESEARCH/scripts/ce_map_scan.py` —
скрипт проверяет утверждения этого документа (раскладку записи, формулу респавна,
lookup по имени, привязку CE-объекта), образ берёт из `GRAFT_SERVER_DIR`.

## Зачем

Задача — менять параметры экономики (types.xml) на работающем сервере, без
рестарта. Движкового API нет; пути два — перечитать файл или писать в реестр
типов напрямую. **Reload не входит в graft** — это отдельная библиотека поверх,
изолирующая адреса CE от ядра лоадера.

## Классы по RTTI (статика)

Около 25 классов `CE*` + `ADBOffline`/`ADBOnline`. Для получения контекста
вызова удобен скриптовый `CEApi` — graft находит точки движка по ванильным
нативам (`function_referencing` по имени натива).

## Идентификация функций (две сборки, статика)

| Адрес (1.30.164200) | Размер | Что это |
|---|---|---|
| `0x1408fbda0` | 0x3e0 | **загрузчик events.xml** (не types.xml!) — `Failed to read events file '%s'`, корень `events`, цикл по `<event>` |
| `0x1408fb6a0` | 0x52a | **парсер одного `<event>`** (не `<type>`) — nominal/restock встречаются и в событиях, и в типах, по этим якорям функции не различить |
| `0x1408fceb0` | ~0x500 | **парсер `<type>`** — точное начало ищется по цепочке .pdata от `0x1408fcf89` |
| `0x1408fd370` | ~0x3b4 | **загрузчик types.xml** |
| `0x1406a8e20` | 0x11a5 | парсер cfgeconomycore.xml |
| `0x1406bd3a0` | 0x839 | парсер полей (quantmin и др.) |

**Внимание:** `0x1408fcf89` — **chained-запись .pdata** (UNW_FLAG_CHAININFO),
кусок разбора `<type>`, а не функция. Если вызвать по этому адресу — сервер
упадёт. Настоящее начало функции — примерно `0x1408fceb0`.

### Реестр дескрипторов (статика)

Реестр файлов экономики `0x1411c9c00`+ — таблица «имя файла → обработчик».
Диспетчер `0x1408fb1b0` — **слот 3 vtable ADBOffline** (виртуальный метод,
прямых вызовов E8/E9 нет). По очереди грузит messages, economy, events,
globals и types. Это закрывает вопрос о том, кто вызывает парсеры.

### Конструктор аддона (статика)

`0x140a93a20` — конструктор объекта аддона (`enf::Item` + `enf::ClassContainer`
+ `DayZAddonManager`). Регистрирует **семь** файлов по умолчанию в полях
`this+0x108` (types.xml) с шагом `0x10` до `this+0x168`:
types, globals, economy, messages, events, cfgspawnabletypes, cfgrandompresets.

### Рантайм-инициализация (статика; на 164078 сверена только фаза Loading core data)

`[CE][Hive] :: Loading core data ... ` — якорь первой фазы рантайма,
`0x1408f43e0` (0x154). Дальше цепочка фаз: `[CE][CoreData]` → `[CE][LoadMap]`
→ `[CE][RegisterConfig]` → `[CE][RegisterBind]` → `[CE][TypeSetup]` →
`[CE][DynamicEvent]` → `[CE][Storage]`.

Функция `[CE][OnInit]` `0x1406bbc40` — пайплайн редактора мира (LoadPrototype,
Clusters, MapExport), на живом сервере не вызывается.

### Штатная конвертация персонажей offlineDB (статика)

`0x1408fa300` (0x539) — не загрузчик, а **миграция персонажей**:
`"SELECT Id, Alive FROM Players"` → `"UPDATE Players SET Data=?, Alive=1
WHERE Id=?"`, лог `"[CE][offlineDB] :: Conversion of characters started."`.
Это потребитель `DB_Versions.Structure` — движок сам апгрейдит BLOB-ы
персонажей между версиями сейва на старте.

## Реестр типов: имя → запись (статика + живой замер)

Запись типа доступна **напрямую из hash table коллекции**, без обхода иерархии:

```
глобал CE-объекта (геттер, см. «Точки входа») → E
  └─ [E+0x20] коллекция типов C
       ├─ [C+0x98] бакеты, шаг 0x18: [+0x04]=state(1=занят),
       │            [+0x08]=хеш имени, [+0x10]=указатель на TYPE ENTRY
       ├─ [C+0xa0]=bucket_count, [C+0xa8]=element_count
       └─ TYPE ENTRY (таблица ниже)
```

Хеш имени — полиномиальный ×0x25 по символам в нижнем регистре, lookup с
open-addressing (функция `0x14069ee40`, вызывается из Estimate; статика).
Имя записи лежит втройным косвенным: `[[[entry+0x10]+0x10]+0x10]` —
C-строка (живой замер).

Числа бакетов — **свойство набора типов, а не движка**: на живом замере
модового сервера 4643 записи в 16384 бакетах (types.xml миссии + моды);
в более раннем замере на другом наборе файлов было 491/1024. Сверка дампа
реестра с types.xml миссии (живой замер): nominal совпал 2374/2374, min —
2202/2374 (расхождения — зомби, их ведёт InfectedRespawner, не types.xml).

**Исправление ранней версии карты:** «wrapper → object → group → type_entry
(4 уровня косвенности)» — неверно; записи читаются прямо из бакетов.
Ранняя пара «+0x2c = на земле, +0x30 = в контейнерах» — тоже неточность:
+0x30 инкрементируется не у самой записи, а у второго объекта по
`[entry+0x98]` (см. «писец счётчиков»).

## Структура TYPE ENTRY (формула — две сборки; поля — статика + живой замер)

| Смещение | Тип | Поле |
|---|---|---|
| +0x1c | float | restock-таймер (гейт спавна в candidate) |
| +0x20 | float | второй таймер |
| +0x2c | int32 | счётчик (инкрементируется Estimate) |
| +0x30 | int32 | счётчик (инкрементируется у объекта `[entry+0x98]`) |
| +0x54 | int32 | **NOMINAL** |
| +0x58 | int32 | **MIN** |
| +0x69 | bool | флаг «in respawn» |
| +0x74 | byte | флаги `count_in_*` (биты 1/2/4/8) |
| +0x88 | int32 | флаги; **бит 5 разрешает респавн** |
| +0x98 | ptr | второй счётчик-объект |

Nominal, min и оба счётчика читаются в формуле респавна из **одного объекта**
— подтверждено на обеих сборках (статика).

## Кто пишет счётчики (1.30.164200, статика)

Счётчики обновляет **Estimate-коллбек** `0x14069ea10(C, entity, ±1)` — все
девять вызывателей передают `rcx = [E+0x20]` (ту же коллекцию), сам вызов
сидит в обработчиках создания/удаления сущностей. По флагам `count_in_*`
(байт +0x74): `inc [entry+0x2c]` и, если у записи есть второй объект
`[entry+0x98]`, — `inc [объект+0x30]`.

Периодического пересчёта/сброса НЕТ: `0x14069e930` (вызов `vtable[0](1)` по
всем записям), который ранняя версия карты считала «сбросом счётчиков перед
проходом», — это Release при разрушении коллекции (вызван из деструктора
`0x1406a5620`). Следствие: значение счётчиков живое, событийно поддерживаемое
(живой замер: на модовом сервере большинство типов стоят ровно на nominal).

## Цикл респавна (зона спавна — две сборки, статика)

```
LootRespawner::Update 0x1406d65a0 — гейты: [this+0x30] initial-done,
  флаг [root+0x70]+8>>4&1, таймеры контекста (+0x24/+0x28, +0x3e/+0x3f)
  └─ sweep 0x1406d67d0 → итератор 0x14069f160 (обход бакетов C)
       └─ respawn candidate 0x1406d6863:
            missing = [entry+0x54] − [entry+0x2c] − [entry+0x30]
            гейты: бит 5 [entry+0x88], кап [объект_типа+0x3c], restock +0x1c
            └─ спавн-тест 0x1406d6050(this, entry, amount, 1)
```

`root` — статический объект CE (геттер `0x1408f40e0`, в теле —
`lea rax,[rip+disp32]; add rsp,0x30; pop rbx; ret`). Байт `[root+0x109]`
включает verbose-логи `[RESPAWN CANDIDATE]` в RPT (живой замер: байт
переключается, логов на пустом сервере не появлялось — см. открытые вопросы).

## Точки входа для плагина (статика + живой замер)

- **CE-объект**: найти SpawnRandomLoot строкой-якорем, затем внутри функции
  (`find_in_function`) паттерн `mov rcx,[rax+0x20]; call` — геттер вызван
  максимум за 8 байт до него, тело геттера — `mov rax,[rip+disp32]; ret`,
  из него извлекается адрес глобала. Проверено живым замером (обе точки
  входа в SpawnRandomLoot дают один глобал). Так делает и
  `ce_map_scan.py`, раздел [5].
- **Фиксированный отступ −0x157b0** от SpawnRandomLoot до lookup-пролога
  `48 83 EC 08 83 79 28 00` совпал между 164200 и 164078, но это случайность
  линковки: при любой перекомпоновке образа он уплывёт. Использовать только
  как историческую сверку, не как паттерн для кода.
- Для записи параметров достаточно чтения бакетов: обход C+0x98 со сверкой
  имени записи — без эвристик по значениям полей.

## Эксперименты (живой замер, 1.30.164200)

### Полный повторный OnInit — отрицательный

Hook-capture на `[CE][Hive] :: Loading core data` (`0x1408f43e0`) из
`GRAFT_ON_LOAD`. При родном буте движок сам вызвал функцию через детур,
`this` CE-объекта захвачен. Повторный вызов через тромплин:

- Фазы прошли полностью (CoreData → TypeSetup → Storage), ~3 секунды
- Сервер пережил вызов, но через ~3 минуты при спавне лута у игрока —
  `0xC0000005` по адресу `0x680942BD` (куча, freed allocation)
- Код: `mov [rdi+10h],eax` — запись в освобождённый объект

**Вывод:** полный повторный `OnInit` пересоздаёт реестры и контейнеры,
а старые ссылки в других частях движка остаются висячими.

### Повторный вызов загрузчика types.xml — отрицательный

Файл перечитывается, но записи воссоздаются со **счётчиками 0**, и цикл
респавна дорабатывает разницу `nominal − 0` сразу по всем типам —
наблюдали ~189 000 заспавненных предметов. Это же объясняет старый вывод
«после reload тип не respawnится»: счётчики терялись. Перезапуск загрузчика
как способ живого обновления не годится.

### HeapWalk + запись nominal — частичный, подход оставлен

Поиск записи перебором аллокаций кучи по паре (nominal, min) ловит чужие
структуры — значения не уникальны, были записи в посторонние объекты.
Запись в +0x30 выбранной аллокации дала `0xe06d7363` — это код C++
исключения MSVC (EH-механизм), а не свидетельство о типе поля; гипотеза
«+0x30 — упакованная структура, не int32» остаётся гипотезой.
После уточнения модели (второй объект по `[entry+0x98]`) надобность в
HeapWalk отпала: записи читаются из бакетов по имени.

### Прямая запись nominal/min в запись по имени — работает, долив не подтверждён

Запись `nominal`/`min` в найденную по имени запись применяется и живёт
(дамп реестра до/после, повторные чтения; негативных эффектов на сервере
не наблюдали). Но подтверждения, что цикл респавна доливает мир до нового
nominal, пока нет: на пустом сервере после записи счётчики не росли
(два типа, две записи, наблюдение ~10 минут, verbose-режим включён).
Открытый вопрос — планирование sweep (см. ниже), проверка следующим шагом —
хук-счётчик на спавн-тест `0x1406d6050`.

### Итог экспериментов

Единственный подтверждённый способ сменить экономику сейчас — **правка
types.xml + рестарт сервера**. Прямая запись в реестр — перспективный путь
(точная адресация доказана), рабочим считается после подтверждения долива.

## Открытые вопросы

1. **Планирование sweep** на пустом сервере: гейты `0x1406d65a0` (таймеры
   контекста, `[root+0x70]`-флаг) — не доливает ли LootRespawner только при
   активных игроках? Проверка: хук-счётчик на `0x1406d6050`.
2. Семантика счётчика `[entry+0x30]`/`[entry+0x98]`-объекта — что именно
   считается вторым счётчиком (контейнеры? группы?).
3. Кап `[объект_типа+0x3c]` (`[entry+0x10]` — объект типа движка): что
   ограничивает (пачка спавна за проход?).

## План реализации reload (отдельная библиотека поверх graft)

1. Точки входа — по якорям и `find_in_function` (раздел выше), без адресов.
2. Обновление параметров — запись в запись по имени (бакеты C+0x98).
3. Пересоздание загрузчиком не использовать: сбрасывает счётчики (эксперимент).
4. Для пересоздания пространственной базы (точек спавна) нужны другие фазы —
   это путь с риском, как показал OnInit-эксперимент.
