# Central Economy DayZ: карта подсистемы и путь к живому reload экономики

Разбор снят с **DayZServer_x64 1.30.164200.56 (retail)**. Выборочно перепроверено
автором graft на **1.30.164078.38**: парсеры из первой версии карты, зона спавна
(SpawnRandomLoot — тот же размер 0x10d0), формула респавна, lookup-пролог.
**Сдвиг между сборками не постоянный**: +0x98d0 у парсеров, +0x96c0 в зоне спавна,
около +0x9960 у `[CE][Hive] Loading core data` — адреса нельзя переносить из
сборки в сборку одним сдвигом, каждая находка перепроверяется паттерном.

Как читать пометки: `(статика)` — офлайн-разбор образа; `(живой замер)` —
поведение на работающем сервере 1.30.164200 (модовый, CF/RaG/Terje); `две сборки`
— сверено и на 164200, и на 164078. Адреса — VA при базе из заголовка
(0x140000000); для рантайма вычесть базу процесса.

Перепроверка после патча игры: `py -3.12 RESEARCH/scripts/ce_map_scan.py` —
скрипт проверяет утверждения этого документа (раскладку записи, формулу респавна,
lookup по имени, привязку CE-объекта), образ берёт из `GRAFT_SERVER_DIR`.

## Зачем

Задача — менять параметры экономики (types.xml) на работающем сервере, без
рестарта. Движкового API нет; пути два — перечитать файл или писать в реестр
типов напрямую. **Reload не входит в graft** — это отдельная библиотека поверх,
изолирующая адреса CE от ядра лоадера.

## Классы по RTTI (статика)

Около 25 классов `CE*` + `ADBOffline`/`ADBOnline`. Для получения контекста
вызова удобен скриптовый `CEApi` — graft находит точки движка по ванильным
нативам (`function_referencing` по имени натива).

## Идентификация функций (две сборки, статика)

| Адрес (1.30.164200) | Размер | Что это |
|---|---|---|
| `0x1408fbda0` | 0x3e0 | **загрузчик events.xml** (не types.xml!) — `Failed to read events file '%s'`, корень `events`, цикл по `<event>` |
| `0x1408fb6a0` | 0x52a | **парсер одного `<event>`** (не `<type>`) — nominal/restock встречаются и в событиях, и в типах, по этим якорям функции не различить |
| `0x1408fceb0` | ~0x500 | **парсер `<type>`** — точное начало ищется по цепочке .pdata от `0x1408fcf89` |
| `0x1408fd370` | ~0x3b4 | **загрузчик types.xml** |
| `0x1406a8e20` | 0x11a5 | парсер cfgeconomycore.xml |
| `0x1406bd3a0` | 0x839 | парсер полей (quantmin и др.) |

**Внимание:** `0x1408fcf89` — **chained-запись .pdata** (UNW_FLAG_CHAININFO),
кусок разбора `<type>`, а не функция. Если вызвать по этому адресу — сервер
упадёт. Настоящее начало функции — примерно `0x1408fceb0`.

### Реестр дескрипторов (статика)

Реестр файлов экономики `0x1411c9c00`+ — таблица «имя файла → обработчик».
Диспетчер `0x1408fb1b0` — **слот 3 vtable ADBOffline** (виртуальный метод,
прямых вызовов E8/E9 нет). По очереди грузит messages, economy, events,
globals и types. Это закрывает вопрос о том, кто вызывает парсеры.

### Конструктор аддона (статика)

`0x140a93a20` — конструктор объекта аддона (`enf::Item` + `enf::ClassContainer`
+ `DayZAddonManager`). Регистрирует **семь** файлов по умолчанию в полях
`this+0x108` (types.xml) с шагом `0x10` до `this+0x168`:
types, globals, economy, messages, events, cfgspawnabletypes, cfgrandompresets.

### Рантайм-инициализация (статика; на 164078 сверена только фаза Loading core data)

`[CE][Hive] :: Loading core data ... ` — якорь первой фазы рантайма,
`0x1408f43e0` (0x154). Дальше цепочка фаз: `[CE][CoreData]` → `[CE][LoadMap]`
→ `[CE][RegisterConfig]` → `[CE][RegisterBind]` → `[CE][TypeSetup]` →
`[CE][DynamicEvent]` → `[CE][Storage]`.

Функция `[CE][OnInit]` `0x1406bbc40` — пайплайн редактора мира (LoadPrototype,
Clusters, MapExport), на живом сервере не вызывается.

### Штатная конвертация персонажей offlineDB (статика)

`0x1408fa300` (0x539) — не загрузчик, а **миграция персонажей**:
`"SELECT Id, Alive FROM Players"` → `"UPDATE Players SET Data=?, Alive=1
WHERE Id=?"`, лог `"[CE][offlineDB] :: Conversion of characters started."`.
Это потребитель `DB_Versions.Structure` — движок сам апгрейдит BLOB-ы
персонажей между версиями сейва на старте.

## Реестр типов: имя → запись (статика + живой замер)

Запись типа доступна **напрямую из hash table коллекции**, без обхода иерархии:

```
глобал CE-объекта (геттер, см. «Точки входа») → E
  └─ [E+0x20] коллекция типов C
       ├─ [C+0x98] бакеты, шаг 0x18: [+0x04]=state(1=занят),
       │            [+0x08]=хеш имени, [+0x10]=указатель на TYPE ENTRY
       ├─ [C+0xa0]=bucket_count, [C+0xa8]=element_count
       └─ TYPE ENTRY (таблица ниже)
```

Хеш имени — полиномиальный ×0x25 по символам в нижнем регистре, lookup с
open-addressing (функция `0x14069ee40`, вызывается из Estimate; статика).
Имя записи лежит втройным косвенным: `[[[entry+0x10]+0x10]+0x10]` —
C-строка (живой замер).

Числа бакетов — **свойство набора типов, а не движка**: на живом замере
модового сервера 4643 записи в 16384 бакетах (types.xml миссии + моды);
в более раннем замере на другом наборе файлов было 491/1024. Сверка дампа
реестра с types.xml миссии (живой замер): nominal совпал 2374/2374, min —
2202/2374 (расхождения — зомби, их ведёт InfectedRespawner, не types.xml).

**Исправление ранней версии карты:** «wrapper → object → group → type_entry
(4 уровня косвенности)» — неверно; записи читаются прямо из бакетов.
Ранняя пара «+0x2c = на земле, +0x30 = в контейнерах» — тоже неточность:
+0x30 инкрементируется не у самой записи, а у второго объекта по
`[entry+0x98]` (см. «писец счётчиков»).

## Структура TYPE ENTRY (формула — две сборки; поля — статика + живой замер)

| Смещение | Тип | Поле |
|---|---|---|
| +0x18 | float | **LIFETIME** (сек; живой замер: запись/чтение) |
| +0x1c | float | **RESTOCK** (сек; гейт спавна в candidate) |
| +0x20 | float | второй таймер |
| +0x2c | int32 | счётчик (инкрементируется Estimate) |
| +0x30 | int32 | счётчик (инкрементируется у объекта `[entry+0x98]`) |
| +0x54 | int32 | **NOMINAL** |
| +0x58 | int32 | **MIN** |
| +0x5c | int32 | **COST** (живой замер) |
| +0x60 | float | **QUANTMIN** (доля = xml/100; живой замер) |
| +0x64 | float | **QUANTMAX** (доля = xml/100; живой замер) |
| +0x69 | bool | флаг «in respawn» |
| +0x74 | byte | флаги `count_in_*` (биты 1/2/4/8) |
| +0x78/+0x7c/+0x80/+0x84 | int32 | маски category/tag/usage/value (бит = позиция имени в cfglimitsdefinition.xml) |
| +0x88 | int32 | флаги; **бит 5 разрешает респавн** |
| +0x98 | ptr | второй счётчик-объект |

Скаляры +0x18/+0x1c/+0x5c/+0x60/+0x64 и маски — проверены живой записью
и чтением (диф types.xml ↔ реестр, 2374 типа × 7 полей = 0 расхождений).

Nominal, min и оба счётчика читаются в формуле респавна из **одного объекта**
— подтверждено на обеих сборках (статика).

## Кто пишет счётчики (1.30.164200, статика)

Счётчики обновляет **Estimate-коллбек** `0x14069ea10(C, entity, ±1)` — все
девять вызывателей передают `rcx = [E+0x20]` (ту же коллекцию), сам вызов
сидит в обработчиках создания/удаления сущностей. По флагам `count_in_*`
(байт +0x74): `inc [entry+0x2c]` и, если у записи есть второй объект
`[entry+0x98]`, — `inc [объект+0x30]`.

Периодического пересчёта/сброса НЕТ: `0x14069e930` (вызов `vtable[0](1)` по
всем записям), который ранняя версия карты считала «сбросом счётчиков перед
проходом», — это Release при разрушении коллекции (вызван из деструктора
`0x1406a5620`). Следствие: значение счётчиков живое, событийно поддерживаемое
(живой замер: на модовом сервере большинство типов стоят ровно на nominal).

## Цикл респавна (зона спавна — статика; поведение — живой замер 2026-11-02)

```
LootRespawner::Update 0x1406d65a0 — гейты: [this+0x30] initial-done,
  флаг [root+0x70]+8>>4&1, таймеры контекста (+0x24/+0x28, +0x3e/+0x3f)
  └─ sweep 0x1406d67d0 → итератор 0x14069f160 (обход бакетов C)
       └─ respawn candidate 0x1406d6863:
            missing = [entry+0x54] − [entry+0x2c] − [entry+0x30]
            гейты: бит 5 [entry+0x88], кап [объект_типа+0x3c], restock +0x1c
            └─ спавн-тест 0x1406d6050(this, entry, amount, 1)
```

Полная цепочка гейтов Update (статика, 164200; `this` → rdi, второй
аргумент-контекст → rbx):

- `[this+0x30] != 0` — initial-done;
- `[[root+0x70]+8] >> 4 & 1` — глобальный флаг разрешённого респавна;
- контекст: `[rbx+0x3e] != 0`, float `[rbx+0x28] >= [rbx+0x24]`,
  `[rbx+0x3f] == 0`, `[rbx+0x40] == 0`;
- состояние `[rbx+8] & 0xf0000`: `0x20000`/`0x80000` → сразу sweep;
  `0x10000`/`0x40000` → sweep только если `[rbx+0x10] < [rbx+0x1c]`;
  прочее → выход.

Объект LootRespawner — единственный со своим vtable, в куче. Прямого
поля CE/root для него НЕТ (обратный поиск указателей, живой замер):
объект — элемент кучевого массива из ~56 апдейтеров (ставятся из
`<updaters>` cfgeconomycore), массив держит менеджер апдейтеров, тоже
в куче. Поэтому резолв — по vtable-слоту Update (слот статически
находит скрипт [6]: глобальный поиск пролога + гейты, без привязки к
соседству), а в рантайме остаётся прицельная сверка vtable у кандидата
из приватной памяти — один раз за бут, с кэшированием. vtable
(164200): база 0x1411683b0, Update — слот +0x58, sweep — +0x78 (4 слота
дальше); конструктор хранит vtable по `lea` в 0x1406c2a79. Контекст для
вызова лежит в самом объекте: `[obj+0x28]` (живой замер: проходит все
гейты, состояние 0x80000).

**Наблюдение одного прогона (2026-11-02, ~1 ч):** на работающем сервере
с игроком онлайн все гейты Update были открыты (initial-done=1,
root-флаг=1, контекст проходил проверки) — но признаков вызова Update
не видно: поля объекта ([+0x74]/[+0x78], лерп в [+0x50]) заморожены,
хук-счётчик спавн-теста 0. Доказательство косвенное (по полям); для
прямого добавлен детур-счётчик на сам Update — наблюдение продолжается,
на ванильных серверах лут респавнится, значит цикл при каких-то
условиях заводится. Рабочий приём независимо от этого — вызвать
спавн-тест напрямую (см. эксперименты).

`root` — статический объект CE (геттер `0x1408f40e0`, в теле —
`lea rax,[rip+disp32]; add rsp,0x30; pop rbx; ret`). Байт `[root+0x109]`
включает verbose-логи `[RESPAWN CANDIDATE]` в RPT (живой замер: байт
переключается, логов на пустом сервере не появлялось — см. открытые вопросы).

## Initial-проход: бут-раскладка по всей карте (статика + живой замер 2026-11-02)

Родной движковый проход, который раскладывает лут по ВСЕЙ карте при старте
сервера, без игроков. Существует всегда и выполняется при каждом буте —
RPT: `[CE][LootRespawner] (PRIDummy) :: Initially (re)spawned:%d, Nominal:%d,
Total in Map:%d at %d (sec)`.

```
вход: слот vtable+0x50 (функция за якорем «Initial Spawn is DISABLED»,
      0x1406d5fd0) — гейты: бит 0 [[root+0x70]+8] (иначе лог DISABLED),
      [this+0x30] != 0
  └─ раскладка 0x1406d5b50 → гейт-хелпер 0x1406d8fd0 по состоянию
      контекста [ctx+0x40]: 1 → нет, 2 → да, 3 → по флагу [ctx+0x3c]
     └─ цикл по всем типам реестра:
          PCT  = [ctx+0x3d]==0 ? [this+0x70] (InitialSpawn%)
                               : [this+0x6c] (RestartSpawn%)
          target = nominal * PCT / 100 (imul + магическое деление на 100)
          дефицит = target − [entry+0x2c] − [entry+0x30] (только > 0)
          гейты типа: (flags88 & 5)==4 (бит2=1, бит0=0), бит7=0, nominal>0;
          при бите 5 дефицит расширяется до полного nominal−counters
          цикл спавн-тестов 0x1406d6050(this, entry, remaining, 1),
          после каждого вызова remaining −= [this+0x98] (число созданного)
```

Поля объекта LootRespawner пишет загрузчик globals.xml — метод за якорем
«RespawnTypes» (0x1406d66c0, слот vtable+0x88), вызывается на самом объекте:
`+0x60` RespawnTypes, `+0x64` RespawnAttempt, `+0x68` SpawnInitial,
`+0x6c` RestartSpawn, `+0x70` InitialSpawn (все — проценты/числа из globals),
`+0x58` LootProxyPlacement (bool), `+0x9c` LootSpawnAvoidance (float).
Оба процента — InitialSpawn И RestartSpawn — участвуют в формуле одинаково
как процент от nominal.

**Ключевые живые факты (2026-11-02, сервер 164200):**

- Хронология бута: globals (хук-loader) → storage restore → initial →
  немедленный CE-save (types.bin/dynamic_*.bin пишутся через ~1 c после
  initial). Дальше периодические сохранения — реже и по условию
  (наблюдались интервалы 10 мин и 27+ мин без save).
- **InitialSpawn=100 / RestartSpawn=0 (ваниль): на персистентном мире
  (storage восстановлен, [ctx+0x3d]!=0) бут-проход берёт RestartSpawn —
  и раскладка вырождается в «(re)spawned:0».** Vicinity-цикл тут ни при
  чём: раскладку «выключает» именно нулевой процент, а не «спящий» sweep.
- Перезапись `[respawner+0x6c]` (RestartSpawn) до прохода (хук
  globals-загрузчика; поля читает только initial) даёт движковую
  раскладку дефицита по всей карте: замер 2382-типовой экономики —
  20801 предмет за 6.8 с, без игроков, точки по всей карте (PRIDummy).
- Счётчики после СКРИПТОВЫХ удалений (Enforce ObjectDelete) падают
  с задержкой (замер: −7032 предмета отразились ровно на −7032 в сумме
  счётчиков в течение минут); до этого чтение дефицита видит старьё.
- Раскладка initial не «знает» про излишек: переспавн сверху не
  срезается (симметрии с vicinity нет), подрезка — внешняя.
- Гейт типа (flags88 & 5)==4 — нормальное состояние записи (замер:
  3641/4321 записей 0x2c); насытившиеся типы движок переводит
  0x12c → 0x10c (снимается бит 5 — гейт periodic-кандидата, initial
  это не блокирует).

## Точки входа для плагина (статика + живой замер)

- **CE-объект**: найти SpawnRandomLoot строкой-якорем, затем внутри функции
  (`find_in_function`) паттерн `mov rcx,[rax+0x20]; call` — геттер вызван
  максимум за 8 байт до него, тело геттера — `mov rax,[rip+disp32]; ret`,
  из него извлекается адрес глобала. Проверено живым замером (обе точки
  входа в SpawnRandomLoot дают один глобал). Так делает и
  `ce_map_scan.py`, раздел [5].
- **Фиксированный отступ −0x157b0** от SpawnRandomLoot до lookup-пролога
  `48 83 EC 08 83 79 28 00` совпал между 164200 и 164078, но это случайность
  линковки: при любой перекомпоновке образа он уплывёт. Использовать только
  как историческую сверку, не как паттерн для кода.
- Для записи параметров достаточно чтения бакетов: обход C+0x98 со сверкой
  имени записи — без эвристик по значениям полей.

## Эксперименты (живой замер, 1.30.164200)

### Полный повторный OnInit — отрицательный

Hook-capture на `[CE][Hive] :: Loading core data` (`0x1408f43e0`) из
`GRAFT_ON_LOAD`. При родном буте движок сам вызвал функцию через детур,
`this` CE-объекта захвачен. Повторный вызов через тромплин:

- Фазы прошли полностью (CoreData → TypeSetup → Storage), ~3 секунды
- Сервер пережил вызов, но через ~3 минуты при спавне лута у игрока —
  `0xC0000005` по адресу `0x680942BD` (куча, freed allocation)
- Код: `mov [rdi+10h],eax` — запись в освобождённый объект

**Вывод:** полный повторный `OnInit` пересоздаёт реестры и контейнеры,
а старые ссылки в других частях движка остаются висячими.

### Повторный вызов загрузчика types.xml — отрицательный

Файл перечитывается, но записи воссоздаются со **счётчиками 0**, и цикл
респавна дорабатывает разницу `nominal − 0` сразу по всем типам —
наблюдали ~189 000 заспавненных предметов. Это же объясняет старый вывод
«после reload тип не respawnится»: счётчики терялись. Перезапуск загрузчика
как способ живого обновления не годится.

### HeapWalk + запись nominal — частичный, подход оставлен

Поиск записи перебором аллокаций кучи по паре (nominal, min) ловит чужие
структуры — значения не уникальны, были записи в посторонние объекты.
Запись в +0x30 выбранной аллокации дала `0xe06d7363` — это код C++
исключения MSVC (EH-механизм), а не свидетельство о типе поля; гипотеза
«+0x30 — упакованная структура, не int32» остаётся гипотезой.
После уточнения модели (второй объект по `[entry+0x98]`) надобность в
HeapWalk отпала: записи читаются из бакетов по имени.

### Прямая запись nominal/min в запись по имени — работает, долив не подтверждён

Запись `nominal`/`min` в найденную по имени запись применяется и живёт
(дамп реестра до/после, повторные чтения; негативных эффектов на сервере
не наблюдали). Но подтверждения, что цикл респавна доливает мир до нового
nominal, пока нет: на пустом сервере после записи счётчики не росли
(два типа, две записи, наблюдение ~10 минут, verbose-режим включён).
Открытый вопрос — планирование sweep (см. ниже), проверка следующим шагом —
хук-счётчик на спавн-тест `0x1406d6050`.

### Прямой вызов спавн-теста с сим-потока — работает (2026-11-02)

Хук-счётчик на `0x1406d6050` (якорь «Item exceeded max tests») простоял
0 вызовов за десятки минут при игроке онлайн и открытом гейте записи —
родной цикл не заводится (см. «Цикл респавна»). Вместо него вызвана
сама функция: `bool(this, entry, amount, 1)` из тика симуляции (та же
нить, что у родного цикла). Объект `this` — LootRespawner из кучи —
найден цепочкой без адресов: якорь спавн-теста → пролог Update
(`mov [rsp+8],rbx; push rdi; sub rsp,0x20; mov rbx,rdx; mov rdi,rcx;
call; cmp byte [rdi+0x30],0; mov rax,[rax+0x20]`) в окне ±0x2000 →
qword-слоты образа, содержащие адрес Update (vtable) → приватная память,
где `[obj]` равен найденному vtable-указателю (проверка: `[obj+0x30]=1`,
`[obj+0x28]` читается). Единственное совпадение на процессе.

Результат: предметы появляются в мире без рестарта — от 0 до счётчика
nominal за секунды; движок сам закрывает бит 5 (0x12c → 0x10c), когда
его счётчики видят насыщение. Раскладка — по валидным точкам лута с
matching usage (Military) по всей карте, не строго вокруг одного игрока.

### amount спавн-теста — пакетный, не жёсткий потолок (2026-11-02)

Один вызов с amount=10 при пустом мире дал ~69 предметов, amount=40 —
~118 (реальное число — дамп позиций по всей карте). Точный множитель
не стабилен (~2–3×): amount задаёт пакет попыток, а не лимит итога.
Рабочая схема — грубый доспавн + точная «подрезка» излишка обходом мира
(у внешнего инструмента это решёточный вайп с лимитом «оставить N»).

### Счётчики не полностью видят форсированный спавн (2026-11-02)

После прямых вызовов событийный счётчик типа показывал 51 при ~118
реальных предметах (дамп). Аналогично после массового удаления объектов
счётчики падают с задержкой в десятки секунд — чтение дефицита сразу
после вайпа видит устаревшие значения. Вывод: счётчики пригодны для
решений движка, но не как источник истины о числе предметов в мире.

### value (Tier1-4/Unique) географически фильтрует точки (2026-11-02)

Биты value подтверждены живой записью: Tier4 -> маска 0x8, Tier1+Unique ->
0x11 (позиция имени в cfglimitsdefinition.xml, как у usage/category).
Семантика (E2E, один тип с usage=Town, nominal 40, вайп + доспавн):
- value пуст -> 74 предмета по всей карте (Черногорск, Tisy, …);
- value=Tier4 -> 7 предметов, средняя Z 11050 — только NW (Tisy/Myshkino);
- value=Tier1 -> 76 предметов, средняя Z 4897 — юг (Черногорск 33,
  Электрозаводск), несколько восточных городов.
Т.е. маска типа ограничивает спавн точками соответствующих зон тиров,
пересекаясь с usage. (Нюанс снят: ранний «одинаковый результат» двух
замеров был артефактом инструмента измерения — он отдаёт кэш до
истечения своего кулдауна; к движку не относится.)

### tag (floor/shelves/ground) фильтрует группы точек (2026-11-02)

Биты как у остальных списков (floor=0x1, shelves=0x2, ground=0x4 —
живая запись). Теги висят на ГРУППАХ mapgroupproto.xml (миссия:
413 floor / 365 shelves / 101 ground), не на точках. E2E (usage=Town,
nominal 40, вайп + доспавн): пустой tag -> 74+ предметов по всей карте;
tag=shelves -> 31 предмет в «полочных» зданиях (крупнейший кластер —
Новодмитровск); tag=ground -> 0 предметов (групп Town с ground-тегом
нет). Маска типа пересекается с тегами группы так же, как usage/value.

### Vicinity-деспавн излишка не наблюдался (2026-11-02)

При nominal=0 и счётчике 45 предметы типа оставались в мире часами
в течение наблюдения 2026-11-02 при ходящем по ним игроке; срезания
излишка циклом не видно —
симметрии со спавном нет (цикл и не вызывался, см. выше). Для сходжения
мира вниз нужен либо рестарт, либо внешнее удаление.

## Реестры лимитов — cfglimitsdefinition (статика + живой замер 2026-11-02)

Парсер `0x1406b8a80` (якорь `cfglimitsdefinitionuser.xml`); держатель —
`[CE+0x10]` (вызывающий: `call <геттер CE>; mov rbp,rax; mov r15,[rax+0x10]`).
cfglimitsdefinitionuser.xml мерджится в документ ДО разбора — именованные
группы `<user name="G"><usage name="A"/>…</user>` (TownVillage, Tier1234…);
в types.xml допустимо `<usage user="G"/>` — маска = OR членов.

Реестры: holder+0x18 categories, +0x20 tags, +0x28 usage, +0x30 value.
Раскладка реестра: `[+0x0]` элементы по 0x10 `{+0x8 индекс, +0xc бит
(1<<i по порядку файла)}`, `[+0x8]` слотов (с запасом — валидные это
ведущие с битом 1<<i), `[+0x18]` бакеты (0x10: +4 state, +8 hash, +0xc
индекс), `[+0x20]` bucket_count, `[+0x28]` флаг лукапов.

Два живых факта: **имена нигде не хранятся** — только хеши ×0x25 (лукап
сравнивает хеш, не строку); после загрузки флаг `[+0x28]` обнуляется —
движок «замораживает» лукапы (живой дамп всех четырёх реестров совпал
с файлами: 8/3/17/5 валидных).

## cfgspawnabletypes: реестр классов и флаги (статика + живой замер 2026-11-02)

Парсер `0x1406bbc40` (якорь `Failed to read cfgspawnabletypes file`);
дескриптор класса берётся `0x1406a80e0(CE, имя)` — find-or-create.

Реестр классов (как у типов, но смещения другие): `[CE+0xb0]` бакеты
(0x18: +4 state, +8 hash, +0x10 дескриптор), `[CE+0xb8]` bucket_count
(32768), `[CE+0xc0]` элементы (13891). **Сравнение хеша беззнаковое** —
hash 0xB897783f знаково отрицателен, знаковый лукап промахивается.

Дескриптор: flags `+0x24` — бит 1 `unique`, бит 2 `hoarder`, бит 0x800
«есть конфиг» (парсер ставит при любой записи типа); `+0x34` id. Имени
в реестре нет (чисто хешевой). `<bind name=...>` — наследование конфига
другого типа. Списки attachments/cargo — векторы на дескрипторе
(живьём не редактируются); флаги unique/hoarder — можно (биты +0x24).
Живой дамп: 733 файловых записи, 0 расхождений с реестром.

## mapgroupproto: реестр групп зданий и маски (статика + живой замер 2026-11-02)

Загрузчик `[CE][LoadPrototype]` `0x1406b93b0`, парсер группы
`0x1406bafc0`, find-or-create группы `0x1406b0e50(коллекция, имя)`.

Реестр групп: `[[CE+0x10]+0x00]` (держатель лимитов владеет и группами):
`[+0x18]` бакеты 0x18-шагом (+4 state, +8 хеш-QWORD, +0x10 группа),
`[+0x20]` счётчик (1024), `[+0x28]` гейт. Хеш ×0x25 lowercase,
сравнение — равенство QWORD (открытая адресация, stride hash*2+1).
Имени в реестре нет.

Группа — C++-объект 0x80 байт с vtable: **usage-маска +0x58,
value-маска +0x5c** (валидация: Land_Shed_M1 usage=0x30 =
Industrial|Farm, байт-в-байт как в файле). Контейнеры группы:
category +0x28, tag +0x2c, usage +0x34. Маски — те же биты
cfglimitsdefinition, что у типов; живая запись маски группы
перенаправляет спавн по типам зданий с ближайшего прохода
(E2E: usage=Military на сарае при файле Industrial,Farm).

cfgrandompresets (попутно): `<cargo name= chance=>`-блоки с предметами;
ссылки из cfgspawnabletypes — `<cargo preset=…/>`; резолвер
`0x1406bd3a0` с предупреждением `Preset (%s) with name '%s' was not
found`; содержимое — векторы (живьём не редактируются).

## Реестр динамических событий — events.xml (статика + живой замер 2026-11-02)

Загрузчик `0x1408fbda0` (якорь `Failed to read events file '%s'`),
парсер одного `<event>` — `0x1408fb6a0` (цепочка .pdata; якорь
`Unknown value of position element when parsing event %s`).

Реестр: `CE → [+0x28]` объект → `[+0x28]` линейный массив `Event*`,
`[+0x34]` счётчик. Никакого хеша — движок ищет событие линейным
strcmp по имени. Имя события — refcounted-строка: `[[ev]+0x10]` — символы.

Раскладка записи события (живой дамп совпал с events.xml байт-в-байт):

| смещение | поле |
|---|---|
| +0x8 | flags: init_random=1, deletable=2, remove_damaged=4; position 0x100 fixed / 0x200 player / 0x400 uniform; limit 0x10000 parent / 0x20000 child / 0x40000 mixed / 0x80000 custom |
| +0x14 / +0x18 / +0x1c | nominal / min / max (int; min клампится к nominal при limit != custom) |
| +0x20 / +0x24 | lifetime / restock (float, сек) |
| +0x2c / +0x30 / +0x34 | saferadius / distanceradius / cleanupradius (float; saferadius парсер дублирует в +0x38) |
| +0xb8 | secondary (refcounted) |

Поля `active` в записи **нет**: события с active != 1 парсер удаляет из
реестра при загрузке — «включить» такое живьём некуда, нужен рестарт.

## cfgeconomycore.xml: несколько файлов экономики и дубли (живой замер 2026-11-02)

`<ce folder="X"><file name="Y" type="types|events"/></ce>` подключает
дополнительные файлы экономики сверх `db\*.xml`; folder — от корня
миссии. Порядок загрузки: db-файл первым, затем зарегистрированные
по порядку перечисления.

Поведение при дубле имени (проверено на частичном дубле, живой сервер;
движок — последовательная запись полей в существующую запись):

- **молча**: ни ошибок, ни предупреждений в логе;
- одна запись на имя, ничего не суммируется;
- **per-field override**: позже загруженный файл перекрывает ТОЛЬКО
  поля, которые явно содержит; отсутствующий тег = «не трогать»,
  значение остаётся от предыдущего файла. Живой тест: db (nominal=10,
  min=6, usage=Military) + модовый файл (nominal=70, без min и usage)
  → реестр: nominal=70, **min=6 и usage=Military сохранились от db**;
- списки — та же логика на уровне тега: есть в сегменте хотя бы один
  `<usage>` (или value/category/tag) → маска пересчитана по этому
  сегменту целиком (перезапись, не слияние); тега нет — прежняя маска.

Практическое следствие: файл-оверрайд может быть частичным (мод меняет
одно поле, не таща блок), но указанный список заменяется целиком.

### Итог экспериментов

Живой reload экономики **подтверждён end-to-end**: запись скалярных
полей в реестр (nominal/min/lifetime/restock/quantmin/quantmax/cost) +
прямой вызов спавн-теста для дефицита + внешний вайп для срезания.
Полный цикл «правка types.xml → применение → вайп лута → доспавн»
выполнен на живом сервере с игроком: один тип поднят 0 → nominal
(счётчик = nominal, бит 5 закрыт сам движком), «сонный» цикл при этом
обойдён прямым вызовом. Ограничения: amount пакетный (~3×), счётчики
запаздывают, деспавн излишка движком не наблюдается.

## Открытые вопросы

1. **Планирование Update** — открыто. Наблюдение 2026-11-02 (один прогон,
   ~1 ч): признаков вызова Update при открытых гейтах и игроке онлайн нет

## План реализации reload (отдельная библиотека поверх graft)

1. Точки входа — по якорям и `find_in_function` (раздел выше), без адресов.
2. Обновление параметров — запись в запись по имени (бакеты C+0x98).
3. Пересоздание загрузчиком не использовать: сбрасывает счётчики (эксперимент).
4. Для пересоздания пространственной базы (точек спавна) нужны другие фазы —
   это путь с риском, как показал OnInit-эксперимент.
5. Доспавн дефицита — прямой вызов спавн-теста `bool(this, entry, amount, 1)`
   с тика симуляции; объект LootRespawner — цепочкой якорь → пролог Update
   → vtable-слот → приватная память (2026-11-02, проверено живым замером).
   amount пакетный: после доспавна излишек подрезается внешним обходом.

## CE Storage: файловый слой persistence (статика + живой замер 2026-11-03)

Дополнено при задаче «вынести persistence сервера во внешнее хранилище».
Факты — своими словами; адреса — VA при базе 0x140000000, сборка
**1.30.164200.56** (розничный сервер, та же, что в шапке). Перепроверка —
`pe.py`, команды в конце раздела.

### Каталог persistence (живой замер)

`mpmissions/<template>/storage_<N>/`, где N — `instanceId` из serverDZ.cfg
(не всегда 1). Состав на Чероруси:

| Файл(ы) | Что |
|---|---|
| `data/dynamic_NNN.bin` | сегментированный слой дропа и построек игроков |
| `data/vehicles.bin`, `zombies.bin`, `animals.bin` | одноимённые слои |
| `data/building_NNN.bin` | постройки (BaseBuildingBase) |
| `data/types.bin` (+ `types.001`… temp-файлы) | реестр/счётчики CE |
| `data/events.bin` (+ сегменты) | события CE |
| `data/doors.bin` | состояния дверей |
| `players.db` | SQLite: `DB_Versions(Id, Structure)`, `Players(Id, Alive, UID CHAR(64) UNIQUE, Data BLOB)` |
| `spawnpoints.bin` | точки спавна игроков |
| `export/mapgroup*.xml` | экспорт описаний групп при буте |

### Функции сохранения/загрузки слоёв (статика)

| Якорь (строка в образе) | Функция | Что |
|---|---|---|
| `[CE][Storage] Saved data file [%d] items.` и `[CE][Storage] Fetching stream [%d] items.` | `0x1406a3990` (0x341) | сохранение слоя / выдача потока; до логов — вызов `0x1408f40e0`: геттер глобальной структуры настроек (байт verbose `+0x102`; в этой же структуре строка-имя режима `cefullremote`) |
| `[CE][Storage] Restoring file "%s".` | `0x14069fc10`, `0x1406c77c0` | чтение файла слоя |
| `[CE][Storage] Restoring file "%s" %d items.` | `0x1406a3e60` | чтение с подсчётом сущностей |
| `players.db` | `0x1408f9c70` | сборка пути к players.db (склейка каталога storage со строкой через `0x1406d0140`) |

Файловый ввод-вывод — не в этих функциях, а ниже по стеку: фасад
`0x140755a60` → чтение целиком `fopen+fread+fclose` (`0x140756d60`) и запись
целью `fopen+fwrite+fclose` (`0x140757f90`), всё через IAT CRT. Живой замер:
в рантайме persistence ходит НЕ через CRT-фасад — слои и players.db
открываются напрямую `CreateFileW` с префиксом `\\?\`. Патч одного fopen
ничего не перехватывает.

### Транспорт и режимы доступа (живой замер)

- всё persistence открывается `CreateFileW(\\?\...)` из образа движка;
- запись слоёв — temp-файл + `MoveFileExW` (`types.001/.002` → `types.bin`);
- SQLite требует консистентности полного набора операций: CreateFileW,
  DeleteFileW (журнал `players.db-journal`), MoveFileExW,
  Get/SetFileAttributesW (проверки существования), CreateDirectoryW.
  Перенаправление только CreateFileW — журнал расходится с базой, и бут
  падает: `!!! [CE][offlineDB] :: Can't prepare data structure: disk I/O
  error` → `[CE][Hive] :: Initialization failed.`;
- файлы слоёв движок держит ОТКРЫТЫМИ без FILE_SHARE_READ: внешний читатель
  обязан открывать с FILE_SHARE_READ|WRITE|DELETE — CRT-чтение (fopen)
  молча проваливается;
- параллельный readonly-доступ к живому players.db из другого потока процесса
  работает (sqlite busy-timeout); хирургический `DELETE FROM Players WHERE
  UID=...` движок переносит — logout-сейв не воскрешает запись (UPDATE по Id,
  согласуется с разделом «Штатная конвертация персонажей»).

### Бут-последовательность (живой замер, строки RPT)

`[CE][Hive] :: Initializing OFFLINE` → `[StorageDirs] :: Selected storage
directory: …` → `Loading core data` → `[CE][offlineDB] :: Conversion of
characters started / Processing N players` → `Loading map data` →
`[CE][offlineDB] :: No Shutdown message present` (признак некорректного
завершения прошлой сессии) → `Loaded N dynamic events M total types` →
`[CE][Storage] Restoring file "…"` по каждому слою → initial-проход
(раздел «Initial-проход» выше). Выбор InitialSpawn/RestartSpawn описан там
же; практически: при успешно восстановленных слоях бут-раскладка даёт
`Initially (re)spawned:0` — двойного лута не возникает.

### Техника подмены хранилища (живой замер, обобщённо)

Слоты файловых операций в IAT ОБРАЗА ДВИЖКА (не процесса) заменяются на
детуры, переписывающие пути с префиксом `storage_<N>\` на подставной
каталог. Условия целостности:

1. полный набор операций (иначе SQLite расходится, см. выше);
2. подставной каталог и подкаталоги (`data`, `export`) создать ДО первого
   обращения движка: CreateFileW каталогов не создаёт, а сам движок создаёт
   их по настоящему пути;
3. наполнять подставной каталог из внешнего хранилища синхронно, до чтения
   persistence движком (GRAFT_ON_LOAD раньше первой фазы Hive);
4. файл, переживший рестарт, новее копии во внешнем хранилище (финальный
   сейв при выключении позже последней выгрузки) — не перезаписывать,
   внешнее хранилище только закрывает отсутствующее;
5. чтение файлов подставного каталога внешним синхронизатором — с полным
   share (см. режимы доступа);
6. недоступность внешнего хранилища на старте — не включать перенаправление
   вовсе: движок продолжит работать с настоящим каталогом без потерь.

### Перепроверка после патча

```
py -3.12 RESEARCH/scripts/pe.py <server.exe> str "[CE][Storage] Saved data file"
py -3.12 RESEARCH/scripts/pe.py <server.exe> riprefs <VA строки>
py -3.12 RESEARCH/scripts/pe.py <server.exe> dis_func <VA функции>
```

Поведенческие факты (какой API открывает persistence, share-режимы,
цепочка бута) проверяются логом RPT живого сервера; счётчик-детур на
CreateFileW печатает первые persistence-пути.
