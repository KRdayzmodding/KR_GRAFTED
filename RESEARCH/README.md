# RE-окружение: DayZ Server

Цель — понять, как движок Enfusion регистрирует `proto native` функции, чтобы
из своей C++-библиотеки (graft-модуль) добавлять собственные нативы, видимые
из скриптов мода (PBO).

## Что уже известно о цели

Компилятор Enforce Script целиком лежит в серверном exe (`enf_scriptcompiler.cpp`,
`enf_scriptcontext.cpp`, `enf_scriptthread.cpp` — пути из ассертов). Строки-маяки
для поиска точки регистрации нативов:

- `Prototype error '%s'` — компилятор не смог связать `proto native` с движком
- `Native functions don't support 'out' arguments '%s'`
- `Engine class '%s' cannot be modded.` / `Sealed type '%s' can't be modded`
- `Game script module entry function "%s" not found!`
- `Can't compile "%s" script module!`

Модули скриптов и точки входа — из `dayz.gproj`: `core / gameLib / game (CreateGame) /
world / mission (CreateMission)`.

### ABI прототипов (декомпиляция ~20 ванильных импл, `re/out/diag/pseudo/`)

| Форма | Как движок зовёт C++ |
|---|---|
| `proto native R f(A...)` | прямой x64 fastcall по сигнатуре; у метода arg0 = this; `string` = `const char*`; `vector` = 12-байтная структура; `owned string` = возврат `const char*` (движок копирует) |
| `proto R f(A...)` | `int64 f(void*** args, var** ret)`: `(*args)[i]` — указатель на значение i-го аргумента (отсюда out/inout), `*ret` — скриптовая переменная (значение +0, тег типа +16, флаги +20) |

Образцы: `IsCLIParam` (нативная, `bool f(char*)`), `string.IndexOf` (`int f(char*,char*)`),
`Math.Sqrt` (маршалируемая, `***a1`), `string.Substring` (маршалируемая + буфер возврата),
`GetHourMinuteSecond` (три out-аргумента через слоты).

### Регистрация

`RegisterGlobal(ctx, name, impl, ret_buf)` / `RegisterMethod(ctx, cls, name, impl, ret_buf, create)`:
последний числовой аргумент — **размер буфера возврата**, а не флаги (в дескриптор кладётся
`alloc(pool, n)`): 0 у `proto native`, 32 у `int.ToString`, 64 у `GetProfileName`,
0x2000 у `string.Format`. Сама регистрация — линковка по имени с уже разобранным прототипом
(`Linking non-existing fuction '%s'` в `sub_1402CF850`).

Рантайм-поиск этих трёх точек без RVA — `discover.py` (и 1:1 в `INCLUDE/graft/scan.hpp`,
только там ещё голосование трёх якорей). На 1.29 Diag и Server результат совпал с `natives.py`.

### Вызов В ДРУГУЮ СТОРОНУ: как движок сам готовит аргументы

Разобрано по интерпретатору `sub_140368880` (`re/out/diag/vm.c`) и подготовке кадра
`sub_1403663B0` (`re/out/diag/pseudo/`). Нужно для обратного направления — звать
движковые `proto` из C++.

Дескриптор функции (тот же, у которого `+8` импл и `+80` флаги — сходится с
`graft::layout`):

| Поле | Что |
|---|---|
| `+8`  | импл (`layout::desc_impl`) |
| `+32` | массив указателей на ДЕСКРИПТОРЫ переменных: сперва параметры, потом локали |
| `+44` | int: всего переменных (параметры + локали) |
| `+80` | флаги (`layout::desc_flags`) |
| `+88` | **uint8: сколько из них параметров** |

Скриптовая переменная в рантайме — **40 байт**, и движок её не «конструирует», а
**копирует шаблон из дескриптора**: `sub_1403663B0` строчками
`*(_OWORD*)(v14-40) = *(_OWORD*)v17; *(_OWORD*)(v14-24) = *(_OWORD*)(v17+16);
*(_QWORD*)(v14-8) = *(_QWORD*)(v17+32);` льёт 40 байт из `((void**)(desc+32))[i]` в
кадр потока (`thread+7248`, вершина в `thread+76`). Раскладка та же, что мы уже читаем
в `read_var`: значение `+0`, тег `+16` (проверено — `*(desc_var+16) & 0xF0000000`),
флаги `+20`; `+32`/`+34` — uint16 размерности статического массива.

**Следствие для graft: шаблон переменной изобретать не нужно — его несёт сама
вызываемая функция.** Чтобы позвать маршалируемый `proto`: взять `n = *(uint8*)(desc+88)`,
скопировать по 40 байт из `((void**)(desc+32))[i]`, положить значение в `+0` по тегу
`+16`, собрать массив указателей и звать импл.

#### Форм вызова ДВЕ, и перепутать их значит упасть

| Что за метод | Как зовётся | Приёмник |
|---|---|---|
| метод настоящего КЛАССА (`PlayerIdentity.GetPlainId`, наши нативы) | `impl(self, void*** args, void** ret)` | объект в rcx |
| статический (`EnScript.GetClassVar`, `Class.CastTo`) | `impl(void*** args, void** ret)` | нет |
| метод ТИПА-ЗНАЧЕНИЯ (`typename.Spawn`, `string.Substring`) | `impl(void*** args, void** ret)` | **первым в блоке** |

Видно прямо в сигнатурах декомпилированных имплов: `typename.Spawn` (`sub_140315FE0`) —
`f(a1, a2)`, где `**(*a1)[0]` это дескриптор класса, а `*a2` — переменная возврата;
`typename.GetModule` (`sub_140306040`) — `f(a1, a2)` с `***a1`; `EnScript.GetClassVar`
(`sub_140306130`) — `f(a1, a2)`, где `(*a1)[0..3]` четыре аргумента. Ни у одного нет
объекта в rcx.

Отсюда же и `desc+88` сходится с объявлением: у методов класса он равен числу
объявленных параметров, у методов типа-значения — на один больше (приёмник тоже
переменная блока). Измерено на живом движке: `string.Substring` 2 объявлено -> 3,
`typename.Spawn` 0 -> 1, `PlayerIdentity.GetPlainId` 0 -> 0, `EnScript.GetClassVar`
4 (static) -> 4.

Первая попытка звать всё трёхаргументной формой дала `0xC0000005`: движок прочитал наш
rcx как массив аргументов. Стоит помнить, что `+88` это не «сколько аргументов у
функции», а «сколько переменных в блоке».

Новые биты флагов функции (`+80`), из той же подготовки кадра:
`0x10` — у функции есть кадр переменных, `0x100000` — аргументы приходят сырым
значением (копируется только 8 байт в `+0`), `0x200000` — не доинициализировать локали.

Зачем это всё: почти весь «второй этаж» скриптового API — маршалируемый, а не нативный.
`typename.Spawn()` (создать любой скриптовый объект), `EnScript.GetClassVar(null, "g_Game", ...)`
(глобальная переменная, то есть корень объектного графа), `ScriptModule.CallFunction`
(позвать скриптовую функцию), `PlayerIdentity.GetPlainId()` — все `proto`, не `proto native`.
Один примитив открывает всё сразу.

### Что оказалось на живом движке (и чего не было в дизассемблере)

Разбор дал форму вызова, но три вещи выяснились только запуском.

**1. Блок аргументов — не массив, а СТРУКТУРА С ДВУМЯ МАССИВАМИ.**

```c
struct { void** values; void** vars; };   // rdx (или rcx у формы без объекта)
```

По `+0` имплы берут указатели на значения, по `+8` — на сами переменные, и пользуются
кто чем: `typename.Spawn` (`sub_140315FE0`) только первым, `EnScript.GetClassVar`
(`sub_140306130`) обоими — через аксессор `sub_1403672C0`, который буквально
`*(*(a1+8) + 8*i)`. Подать один голый массив значит уронить вторую половину функций.
Значение живёт в самой переменной по `+0`, поэтому у нас оба массива — один и тот же.

**2. Тип переменной движок берёт по полю `+24`, а не по тегу.**

```c
sub_140367280(var) = (*(void**)(var+24))[104][tag & 0xFFFFFFF]
```

Отсюда и правило «переменную не сочинять»: с верным тегом, но пустым `+24` разрешение
типа падает на `[rcx+0x68]`, где rcx = 0 (проверено). Переменной возврата дескриптор
функции не носит, поэтому шаблон для неё берётся у чужого параметра того же типа —
доноры перечислены в `INCLUDE/graft/callout.hpp`.

**3. `void` в объявлении параметра — это семейство `0x7`, а не ноль.**
Снято с дескриптора `EnScript.GetClassVar`: `p0=0x60000005 p1=0x50000003 p2=0x20000000
p3=0x70000004`. Означает «любой тип»: настоящую переменную движок собирает на месте
вызова по фактическому аргументу.

**Про саму GetClassVar** (проверено и из C++, и из скрипта):
- **код возврата врёт** — 0 даже на успешном чтении, при верном значении в out-аргументе;
- **глобальные переменные она не отдаёт** — `g_Game` даёт null и скрипту тоже. Поэтому
  корень объектного графа graft получает от мода вместе с тиком.

### Препроцессор в ванильных скриптах

1452 `#ifdef`, 346 `#ifndef`, 254 `#else`, 1798 `#endif` — и **ни одного составного
`#if`**. Условие любого объявления это конъюнкция простых «определён / не определён»,
поэтому разобрать его легко. А вот РАЗРЕШИТЬ нельзя: какие дефайны были у запущенной
игры, не говорит никто, кому можно верить.

Поэтому `graft apigen` запекает объединение всех веток, а не выбирает одну: методы,
поля и обе цепочки наследования (`class Man extends Person` против
`class Man extends EntityAI`). Чего в конкретной сборке нет, то просто не найдётся в
рантайме — и это дёшево, потому что поиск дескриптора прекращается после восьми
промахов (замер: 1.19 против 1.24 у обычного вызова, то есть добавленной цены нет).

Заодно нашлась потеря, к дефайнам отношения не имеющая: `class IEntity: Managed` —
двоеточие без пробела прилипало к имени, и класс отбрасывался ЦЕЛИКОМ. Вместе с IEntity
пропадали `GetOrigin`/`GetID`/`GetName` у каждой сущности мира. После правки разбор
даёт 6079 классов вместо 4959 и 3266 объявлений вместо 2950.

## Падение нашего кода: чьё оно

В проекте было записано, что SEH в этом процессе не работает — «движок ставит свой фильтр
и валит процесс раньше нашего `__except`». **Это неверно**, и разбор с экспериментом
показывают почему.

### Что движок ставит на самом деле

```c
sub_14037ED60:
    AddVectoredExceptionHandler(0, Handler);          // 0 — в КОНЕЦ списка
    SetUnhandledExceptionFilter(TopLevelExceptionFilter);
    signal(SIGABRT, sub_14037EDA0);

Handler(info):
    if (code == 0xC0000374)  return TopLevelExceptionFilter(info);   // порча кучи
    SetUnhandledExceptionFilter(TopLevelExceptionFilter);            // просто пере-арм
    return 0;                                                        // CONTINUE_SEARCH
```

Три следствия:

1. Их VEH зарегистрирован **с First = 0**, то есть встаёт в конец списка — перед ним
   можно встать своим с First = 1, если однажды понадобится.
2. На первом проходе он **ничего не делает** для всего, кроме порчи кучи: возвращает
   `CONTINUE_SEARCH`. Значит кадровый обработчик получает своё раньше верхнего фильтра.
3. `TopLevelExceptionFilter` (0x14037dbd0) форматирует описание, пишет минидамп
   (`sub_14036E8C0` -> `MiniDumpWriteDump`) и возвращает 0 — процесс умирает штатным
   путём. Зовётся он ТОЛЬКО когда кадрового обработчика не нашлось.

`0xC0000374` (порча кучи) остаётся смертельной по замыслу движка, и это правильно:
продолжать после неё нельзя.

### Почему `__except` раньше «не работал»

Дело не в движке, а в **диапазоне области**. У x64-SEH таблица областей описывает
ДИАПАЗОНЫ АДРЕСОВ; обращение по нулю, написанное прямо в защищённой функции, компилятор
разместил вне этого диапазона, и обработчик не нашёлся. Проверено обеими сторонами:

| как написан сбой | результат |
|---|---|
| разыменование прямо в теле `__try` | процесс умер, `mov eax,[0]` по RVA нашей DLL |
| то же в отдельной `noinline` функции, вызов внутри `__try` | **поймано**, вернулась метка |

Значит падение внутри натива можно забрать у игры: обернуть трамплин, вернуть значение
по умолчанию и написать в журнал, кто именно упал.

**И это бесплатно.** Замер `Perf_HotPathBudget` со защитой на ВСЕХ трамплинах:
`bridge 1.15` против `1.21` у той же сборки без защиты, `guarded 0.97` — разницы нет
вовсе, она внутри шума.

## Карта кадра: от точки входа потока до нашего трамплина

Снята с настоящего минидампа (`cdb -z <dump> -c ".ecxr; k"`), имена — из IDA:

```
__scrt_common_main_seh          CRT main
  sub_1405D9A70
    sub_140C6A5D0
      sub_1404863C0
        sub_140C5F540
          sub_140C68F30
            sub_140AD1060
              sub_1403662A0
                sub_140368880    интерпретатор байткода
                  sub_140368220
                    sub_140367E30
                      sub_140C6E880  -> наш трамплин
```

Карта пригодилась не для хука, а для одного вывода: главный цикл и интерпретатор лежат на
ОДНОМ стеке, значит скриптовый поток и есть главный. Сам хук в итоге не понадобился — см.
ответ выше. Вопрос «законен ли вызов движковых `proto` ВНЕ скриптового вызова» так и
остался открытым, и теперь он неактуален: подмена ванильного натива ставит нас ВНУТРЬ
скриптового вызова, где всё законно по построению.

### ОТВЕТ: хук на движковую точку входа скриптового OnUpdate

Задача решена, и решение — в движке, а не в ванильных скриптах. Раз в кадр движок зовёт
`DayZGame.OnUpdate(bool doSim, float timeslice)` через общую пару «собрать кадр вызова по
индексу» + «исполнить»:

```
lea  rdx, "OnUpdate"          якорь
call sub_140348F40            найти индекс метода по имени
mov  cs:dword_14114D630, eax  индекс кэшируется — отсюда берём адрес кэша
cvtss2sd xmm0, xmm6           timeslice во фрейм: ЭТОТ OnUpdate с float
mov  r8d, eax                 индекс
call sub_140346CF0            собрать вызов   <- хук
call sub_140366A10            исполнить
```

Найдено в `sub_140602380` — это `CGame::Update`. Ищется рантаймом строковым якорем, как
`RegisterGlobal` и `FindClass`: строк `"OnUpdate"` в образе одна на всех (имя события),
ссылок на неё несколько — виджеты, техника, игра, — и нужную отличает `cvtss2sd` между
поиском индекса и сборкой вызова: float-аргумент есть только у кадрового.

**Перенаправляется МЕСТО ВЫЗОВА, а не функция**, и это стоило трёх падений сервера,
прежде чем стало понятно. «Собрать вызов» — общая функция, её зовут из 369 мест, и у
каждого свои аргументы: где-то вещественное число едет в xmm2, где-то нет. Детур на C++
поверх такой функции затирает xmm — компилятор считает их своими, — и ЧУЖОЙ вызов уезжает
в движок с испорченным аргументом. На пустом сервере скрипт зовут редко и всё выглядит
рабочим; живой сервер зовёт постоянно и с вещественными аргументами. Отчёты о падении
показывали ровно это: чтение по `0` и по `-1` в движке, четырьмя кадрами выше нашего.

Поэтому патчится сам `call` в `CGame::Update`: к нам приходит ровно то, что кладёт это
место, и только оно. Ни чужих вызывающих, ни совпадений индексов, ни игры с регистрами.
Само место найдено якорем, начало функции при этом не нужно — а его в рантайме и взять
неоткуда, границ функций у нас нет.

rel32 дотягивается на ±2 ГБ, а образ игры и наша библиотека разъезжаются на сотни (по
отчётам о падении — 546 ГБ), поэтому рядом с местом вызова кладётся заплатка с абсолютным
переходом, и `call` направляется в неё.

Промежуточный вариант — хук на функцию с отбором по индексу метода — не годится ещё и по
второй причине: индекс НУМЕРУЕТ МЕТОД ВНУТРИ КЛАССА, то же число у другого класса значит
другой метод. Плюс движковый кэш до первого разрешения хранит `-1`, и вызов с
неразрешённым индексом совпадал с ним «успешно».

| что | замер |
|---|---|
| частота | ровно раз в кадр |
| поток | скриптовый |
| корень | объект `CGame` первым аргументом, равен `GetGame()` |
| dt | `timeslice` пятым аргументом — тот же, что получает ванильный `OnUpdate` |

**Законен ли вызов движкового `proto` из этой точки** — вопрос, открытый всё исследование.
Ответ: почти полностью. Замер из обработчика тика, 8 кадров подряд:

| результат вызова | как прошло |
|---|---|
| числовой (`EnScript.GetClassVar`) | 8 из 8, ни одного промаха |
| объектный (`typename.Spawn`) | 8 из 8 |
| **строковый** (`typename.GetModule`) | 0 из 8: вызов проходит, строка **пустая** |

Значит дело не в форме вызова и не в отсутствии скриптового кадра как такового, а именно
в пути возврата строки. Это следующая задача.

**Что НЕ сработало** — чтобы не пробовали заново:

| кандидат | почему нет |
|---|---|
| `MsgWaitForMultipleObjects` | в NO_GUI-сервере не зовётся ВООБЩЕ: 0 вызовов |
| `Sleep` | бьётся на чужом потоке — звать движок оттуда нельзя |
| `GetGame` через `RegisterGlobal` | движок вносит эту глобаль не через регистрацию |
| подмена ванильного `CGame.IsServer` | работала (1.3–2.6 вызова на кадр, корень и поток верные), но держалась на том, что `MissionBase.OnUpdate` спрашивает «я сервер?», и тянула ещё две зависимости от чужих скриптов: `EnProfiler.GetGameFrame` ради отсечки кадров и приватное поле `m_DeltaTime` ради dt |
| `CGame.GetTickTime()` как метка кадра | живые часы с разрешением в миллисекунду, а пустой сервер идёт 2474 кадра/с — 3106 вызовов дали 89 различных значений |
| `proto_invoke` для статического `GetGameFrame` | отвергает `self == nullptr` и бросает поиск после восьми промахов — нужна статическая форма и дескриптор, найденный один раз |

### Побочно: кадр потока в этом пути не участвует### Побочно: кадр потока в этом пути не участвует

Первое подозрение было очевидным — «скриптовый кадр лежит в TLS, и вне скриптового вызова
его там нет». Проверено (`re/scripts/frame.py`, вывод в `re/out/diag/frame.txt`): в образе
336 функций читают `gs:[58h]` напрямую, и **ни одной** из них нет ни в самих импл-функциях
разбора аргументов (`sub_1403672C0`, `sub_140367280` — обе листовые), ни в достижимых на
три уровня из подготовки кадра и вызова натива (`sub_1403662A0`, `sub_140367E30` — по 8
функций, TLS не трогает никто).

Кадр потока берётся по явной цепочке указателей (`thread+7248`), а не из TLS. Мы же зовём
`impl` напрямую, минуя интерпретатор, и блок аргументов строим сами — значит «нет текущего
скриптового вызова» этому пути не мешает **по построению**.

Чего это НЕ доказывает: у конкретного натива могут быть свои требования к состоянию
движка (аллокация скриптовых объектов, текущий контекст, стадия кадра). `typename.Spawn`
вне скриптового вызова этим и опасен — не разбором аргументов, а тем, что он делает
внутри. Решающий эксперимент прежний: хук на функцию из карты выше в diag-сборке и вызов
`Spawn` оттуда.
