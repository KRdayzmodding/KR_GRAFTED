# Дефайны скриптового препроцессора: откуда они берутся

Всё ниже добыто на 1.29 двумя способами сразу: разбором `DayZDiag_x64.exe` /
`DayZServer_x64.exe` / `DayZ_x64.exe` и запуском диаг-сервера с разными наборами модов.
Проверочная строка одна, её печатает сам движок на каждый скриптовый модуль:

```
Module: GameLib; loaded 13x files; 13x classes; ... defines: "DAYZ_1_29,SERVER_FOR_WINDOWS,
SERVER,PLATFORM_WINDOWS,DIAG,DIAG_DEVELOPER,NO_GUI,NO_GUI_INGAME,sakhal,MY_MOD,DayZ,
FEATURE_CURSOR,...,LOG_TO_FILE,LOG_TO_SCRIPT"; CRC32: 00000000
```

## Четыре источника

| Откуда | Область | Чем доказано |
|---|---|---|
| имя КЛАССА в `CfgMods` | глобально, все модули | `@MY_MOD` без единого `defines[]` даёт дефайн `MY_MOD` |
| `defines[]` у класса мода | глобально, все модули | CF даёт `CF_MODULES`, `CF_MODSTORAGE`, ... |
| `defs > <x>ScriptModule > value` | с этого модуля и ниже | VPP: `VPPADMINTOOLS` появляется только с модуля `Game` |
| сам движок | глобально | `DAYZ_1_29`, `SERVER`, `PLATFORM_WINDOWS`, `DIAG`, `FEATURE_*` |

Имя берётся именно от КЛАССА, а не от `name=` или `dir=`: Community Framework с
`name="Community Framework"` даёт `JM_CommunityFramework` (имя класса), VPPAdminTools —
`AVPPAdminTools`, а у мода без `dir` и `name` дефайн всё равно есть.

Элемент `defines[]` — либо строка, либо пара `{"ИМЯ", 0|1}` (второе — «объявлен, но
выключен»). Что угодно ещё пропускается с предупреждением
`[CfgMods::Defines] :: [Warning] :: Skipping malformed define entry at index %i.`

Дефайны аддона ГЛОБАЛЬНЫ, и это важно: мод, который кладёт файлы только в `1_Core` и
`3_Game`, виден по имени и в дефайнах `GameLib`, куда он не приносит ничего. Значит,
дописывать свой дефайн можно в любой аддон, а не обязательно в «свой».

**Кроме модуля `Core` (`1_Core`): он компилируется БЕЗ дефайнов вообще.** Строки `Module:`
для него движок не печатает, а проверка пробой (сервер 1.29, `@SIXW_GRAFT`, 2026-09-14):
классы под `#ifdef SIXW_GRAFT` (имя мода), `#ifdef DIAG` (движок) и `#ifdef GRAFTED` в
файле `1_Core` из `3_Game` не видны, класс под `#ifdef GRAFTED_SIXW_GRAFT` в `3_Game` —
виден. Поэтому `graft protogen` не оборачивает объявления `1_Core` в `#ifdef`.

Перепроверено без каскада ошибок компилятора: функция в `1_Core`, собирающая строку из
веток `#ifdef DIAG / SERVER / DAYZ_1_29 / UTESTS_RUN / SIXW_GRAFT / GRAFTED /
GRAFTED_SIXW_GRAFT`, вернула ПУСТО; та же функция в `3_Game` — все семь.

Где это в движке (DayZDiag 1.29, адреса IDA):

- модули создаёт `sub_14050BC40` пятью вызовами фабрики `sub_140357BC0(проект, имя,
  файлы, ?, маска)`. Маска у GameLib `0x200000`, у Game/World/Mission `0x2000000`, а у Core
  — не константа, а поле движка `*(*(qword_141269100+120)+40)`;
- компиляция модуля — `sub_1402D37A0(машина, файлы, n, ctx)`, её находит строка
  `Module: %s; loaded ...`. Дефайны, по которым идёт препроцессор и которые она печатает,
  лежат в `*(ctx)+88`: массив `{CStr имя; u32 флаг}` по 16 байт, счётчик в `+100`;
- список собирает поставщик `sub_1404D1810` (SERVER/PLATFORM/DIAG — безусловно, остальное
  по битам маски). Раз у Core не видны даже безусловные — поставщик для него не зовётся
  вовсе, а не отфильтровывает.

Отсюда путь сделать `#ifdef` рабочим в `1_Core`: врезка в `sub_1402D37A0` (якорь — та же
строка) и дописывание в `*(ctx)+88` ТОЛЬКО `GRAFTED` и `GRAFTED_<ИМЯ>`. Все движковые
дефайны туда класть нельзя: ванильный `1_Core` сам ветвится на `DIAG_DEVELOPER`,
`COMPONENT_SYSTEM`, `GAME_TEMPLATE` — и скомпилировался бы иначе, чем задумано.

## Ключ `-scrDef=ИМЯ`

Работает, принимает несколько повторов (разбор идёт по всей таблице аргументов), но
существует ТОЛЬКО в диаг-сборке: в `DayZServer_x64.exe` и `DayZ_x64.exe` строки `scrDef`
нет вообще. Подменять командную строку ради дефайна поэтому бессмысленно — на боевом
сервере это не работает.

## Где это в движке

`enf::AddonManager::Load` обходит `CfgMods` (сначала основной конфиг, потом каждый мод) и
на каждый класс зовёт «добавить аддон». Та разбирает члены класса —
`dependencies, defs, name, author, authorID, version, extra, type, inputs, ceTypes,
economy, globals, messages, events, spawnableTypes, randompresets, defines`, а внутри
`defs` — `files[]` и `value` — и складывает результат в `enf::CAddon` (104 байта):

| Смещение | Что |
|---|---|
| +0x08 | массив описаний скриптовых модулей (указатель, ёмкость, счёт) |
| +0x18 | массив путей скриптовых модулей |
| +0x28 | массив дефайнов: элемент 16 байт — `{const char* имя; bool включён}` |

Обе «дописать в массив» — крошечные листовые функции одной формы:

```
mov eax, [rcx+count]      счётчик
lea r64, [rcx+array]      массив, причём count == array + 12
shl rax, 4                шаг 16 байт -> дефайны; без него шаг 8 -> пути
```

Этим они и ищутся в рантайме, без адресов: строка-маяк `[CfgMods::Defines] ...` лежит
внутри разбора `CfgMods`, от ссылки на неё смотрим вызовы в окне ±0x400 и отбираем по
форме. На всех трёх бинарях 1.29 обе находятся однозначно, лишних совпадений в окне нет.
Так сделан [SRC/graft/defines.cpp](../../SRC/graft/defines.cpp).

## Строка движка (`enf::CStr`)

Массив дефайнов хранит сырой `const char*`, но потребители берут длину из шапки перед
символами, а не `strlen`:

```
[p-6] u16 ёмкость (вместе с нулём)
[p-4] u16 длина
[p-2] u16 счётчик ссылок
[p ]  символы, заканчиваются нулём
```

Освобождается строка своим аллокатором, когда счётчик доходит до единицы, — поэтому
строка, отданная движку из чужой кучи, обязана иметь счётчик заведомо больше единицы.

## Чем перепроверить после патча игры

```powershell
# 1. Якорь и обе точки: тот же алгоритм, что в рантайме, но по файлу.
python RESEARCH\scripts\pe.py "<игра>\DayZDiag_x64.exe" str "[CfgMods::Defines]"

# 2. Живьём: любой мод с плагином, дальше искать строку `defines:` в script-логе.
#    Должны появиться GRAFTED и GRAFTED_<ИМЯ ПЛАГИНА>.
```

Признак, что форма уехала: в журнале `graft` вместо строки
`addon defines: AddScriptModulePath=... AddDefine=...` стоит
`! addon defines: CfgMods parser not found (...)`.
