# Падения: чьё и почему

Что движок ставит обработчиком на самом деле и почему `__try/__except` в моде
долго считался неработающим.

## Падение нашего кода: чьё оно

В проекте было записано, что SEH в этом процессе не работает — «движок ставит свой фильтр
и валит процесс раньше нашего `__except`». **Это неверно**, и разбор с экспериментом
показывают почему.

### Что движок ставит на самом деле

```c
sub_14037ED60:
    AddVectoredExceptionHandler(0, Handler);          // 0 — в КОНЕЦ списка
    SetUnhandledExceptionFilter(TopLevelExceptionFilter);
    signal(SIGABRT, sub_14037EDA0);

Handler(info):
    if (code == 0xC0000374)  return TopLevelExceptionFilter(info);   // порча кучи
    SetUnhandledExceptionFilter(TopLevelExceptionFilter);            // просто пере-арм
    return 0;                                                        // CONTINUE_SEARCH
```

Три следствия:

1. Их VEH зарегистрирован **с First = 0**, то есть встаёт в конец списка — перед ним
   можно встать своим с First = 1, если однажды понадобится.
2. На первом проходе он **ничего не делает** для всего, кроме порчи кучи: возвращает
   `CONTINUE_SEARCH`. Значит кадровый обработчик получает своё раньше верхнего фильтра.
3. `TopLevelExceptionFilter` (0x14037dbd0) форматирует описание, пишет минидамп
   (`sub_14036E8C0` -> `MiniDumpWriteDump`) и возвращает 0 — процесс умирает штатным
   путём. Зовётся он ТОЛЬКО когда кадрового обработчика не нашлось.

`0xC0000374` (порча кучи) остаётся смертельной по замыслу движка, и это правильно:
продолжать после неё нельзя.

### Почему `__except` раньше «не работал»

Дело не в движке, а в **диапазоне области**. У x64-SEH таблица областей описывает
ДИАПАЗОНЫ АДРЕСОВ; обращение по нулю, написанное прямо в защищённой функции, компилятор
разместил вне этого диапазона, и обработчик не нашёлся. Проверено обеими сторонами:

| как написан сбой | результат |
|---|---|
| разыменование прямо в теле `__try` | процесс умер, `mov eax,[0]` по RVA нашей DLL |
| то же в отдельной `noinline` функции, вызов внутри `__try` | **поймано**, вернулась метка |

Значит падение внутри натива можно забрать у игры: обернуть трамплин, вернуть значение
по умолчанию и написать в журнал, кто именно упал.

**И это бесплатно.** Замер `Perf_HotPathBudget` со защитой на ВСЕХ трамплинах:
`bridge 1.15` против `1.21` у той же сборки без защиты, `guarded 0.97` — разницы нет
вовсе, она внутри шума.
