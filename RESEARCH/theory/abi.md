# ABI и раскладка движка

Как устроены прототипы, регистрация нативов, смерть объекта и вызов в обратную
сторону. Всё, что нужно, чтобы движок и C++ понимали друг друга.

## Найдено (1.29.0.163451)

| Адрес | Что это |
|---|---|
| `sub_1402BF3D0` | разбор объявления функции в компиляторе: `Multiple declaration of function`, `Method '%s' is linked as static/external but declared as member`, `Native functions don't support 'out' arguments` |
| `sub_140533250` | загрузка скриптового модуля, ищет точку входа (`Game script module entry function "%s" not found!`) |
| `sub_140118010` | логгер ошибок компиляции — `(ctx, "формат", ...)`, удобная точка для поиска остальных веток |

Биты флагов функции (поле `+80` у дескриптора), выведены из `sub_1402BF3D0`:
`0x20` — native, `0x4`/`0x4000` — static/external, `0x800` — modded, `0x400` — форвард-объявление.

### ABI прототипов (декомпиляция ~20 ванильных импл, `RESEARCH/out/diag/pseudo/`)

| Форма | Как движок зовёт C++ |
|---|---|
| `proto native R f(A...)` | прямой x64 fastcall по сигнатуре; у метода arg0 = this; `string` = `const char*`; `vector` = 12-байтная структура; `owned string` = возврат `const char*` (движок копирует); возврат `vector` — через скрытый буфер, и его место выбирает бит `0x4000` (см. ниже) |
| `proto R f(A...)` | `int64 f(void*** args, var** ret)`: `(*args)[i]` — указатель на значение i-го аргумента (отсюда out/inout), `*ret` — скриптовая переменная (значение +0, тег типа +16, флаги +20) |

Образцы: `IsCLIParam` (нативная, `bool f(char*)`), `string.IndexOf` (`int f(char*,char*)`),
`Math.Sqrt` (маршалируемая, `***a1`), `string.Substring` (маршалируемая + буфер возврата),
`GetHourMinuteSecond` (три out-аргумента через слоты).

**`external` — это форма импла, а не украшение объявления** (2026-10-01, DayZDiag 1.29,
кейс `Diag_MethodFlags`). Обычный `proto native` метода собран функцией-членом C++:
`this` в rcx, скрытый буфер под `vector` — в rdx (`Object.GetPosition`, флаги `0xa28`,
импл `+0x4A2F50`). `proto native external` — свободная функция с объектом аргументом:
буфер в rcx, объект в rdx (`IEntity.GetOrigin` / `CoordToParent`, `0x4a28`). Движок
выбирает форму вызова по биту `0x4000`: наш метод класса (`0xa28`) он зовёт как
функцию-член — трамплин, принимавший буфер первым, писал результат поверх шапки объекта
и ронял сервер (`Fields_VectorThroughPointer`). Возврату в регистре всё равно: this в rcx
у обеих форм.

### Регистрация

`RegisterGlobal(ctx, name, impl, ret_buf)` / `RegisterMethod(ctx, cls, name, impl, ret_buf, create)`:
последний числовой аргумент — **размер буфера возврата**, а не флаги (в дескриптор кладётся
`alloc(pool, n)`): 0 у `proto native`, 32 у `int.ToString`, 64 у `GetProfileName`,
0x2000 у `string.Format`. Сама регистрация — линковка по имени с уже разобранным прототипом
(`Linking non-existing fuction '%s'` в `sub_1402CF850`).

Рантайм-поиск этих трёх точек без RVA — `discover.py` (и 1:1 в `INCLUDE/graft/scan.hpp`,
только там ещё голосование трёх якорей). На 1.29 Diag и Server результат совпал с `natives.py`.

### Смерть объекта: где её ловить (и почему не в деструкторе)

Вопрос практический: у класса, чьё состояние живёт в C++, кто-то должен сказать нам о
смерти объекта. Напрашивается объявить деструктор нативом — как у движковых
`proto void ~Widget();` (`EnWidgets.c`) и `proto private void ~Shape();` (`EnDebug.c`).
**Так не работает**, и вот два барьера, оба проверены на живой игре (1.29.163709 Diag).

**1. Индекс деструктора компилятор берёт из СЧЁТЧИКА, а не из найденной функции.**
`sub_14032F9B0` на объявлении с `~` пишет `класс+194 = класс+116` — то есть «сколько
функций у класса сейчас», а сам индекс достаётся вычитанием единицы (видно в проверке
hybrid-класса `sub_1403341D0`: `sub_140349210(класс, v194 - 1)`, а 0 значит «деструктора
нет»). Компилятор считает, что объявляемую функцию только что добавили. Натив,
зарегистрированный РАНЬШЕ разбора мода, счётчик не растит — и деструктором класса
становится последний зарегистрированный метод: в игре это
`Cannot call constructor or destructor 'KeyAt' method directly!` на обычном вызове.

**2. Вызов деструктора у скриптового класса всегда уходит в интерпретатор.** Флаги
дескриптора при этом не смотрят: пять прогонов, каждый — падение с одним и тем же
адресом внутри интерпретатора (RVA `0x36bc03`).

| Что пробовали | Флаги дескриптора | Итог |
|---|---|---|
| `proto void ~Класс();` (маршалируемый) | `0xc48` | падение |
| `proto native void ~Класс();` | `0xc28` | падение |
| дескриптор сделан компилятором, импл подставлен позже | `0x828` | падение |
| класс помечен «движковым» битом `0x4000` | — | падение |
| шаблонный класс и обычный | — | падение одинаковое |

Ванильные `~Widget` и `~Shape` живы не поэтому: это движковые классы, их разрушает C++
самого движка.

#### Где движок разрушает объект на самом деле

Разобрано по стеку того самого падения (`cdb -z <дамп>.mdmp -c ".ecxr; k 15; q"`) и
дизассемблеру. У дескриптора класса своя C++ таблица; её **слот 8** (`0x2dc850`) и есть
освобождение объекта:

```
dtor_slot8(rcx = дескриптор класса, rdx = объект):
    call 0x346c50            ; скриптовый деструктор, если он есть (тут и падало)
    ...
    jmp  0x348c10            ; освобождение самого объекта
0x348c10:
    call 0x347860            ; поля объекта
    mov  rax, [объект]       ; <-- C++ ТАБЛИЦА САМОГО ОБЪЕКТА
    xor  edx, edx
    call qword ptr [rax]     ; <-- слот 0: MSVC scalar deleting destructor
    ...                      ; возврат в пул, счётчик ссылок
```

**Слот 0 таблицы самого объекта** — вот чем чистят себя `array`, `map` и `set`:
скриптового деструктора у них нет и не нужно, память освобождает C++ движка. Это же
видно и в дескрипторах классов: у `map`/`array`/`set` своя таблица (RVA `0xe25ef8`,
`0xe25e08`, `0xe25e80`) против общей у скриптовых классов (`0xe1f7d8`, у шаблонных
`0xe1f8d0`), и различаются они ровно в двух слотах — 0 (деструктор дескриптора) и 12.

Отсюда и решение в библиотеке (`SRC/graft/objects.cpp`): объекту, за которым стоит
состояние плагина, хост подменяет таблицу на СВОЮ копию — нулевой слот наш, остальные
как были, — и движок сам зовёт нас там же, где звал бы себя. В скрипте не появляется
ни строчки. Копия делается одна на исходную таблицу, длина считается по подряд идущим
адресам машинного кода.

### Вызов В ДРУГУЮ СТОРОНУ: как движок сам готовит аргументы

Разобрано по интерпретатору `sub_140368880` (`RESEARCH/out/diag/vm.c`) и подготовке кадра
`sub_1403663B0` (`RESEARCH/out/diag/pseudo/`). Нужно для обратного направления — звать
движковые `proto` из C++.

Дескриптор функции (тот же, у которого `+8` импл и `+80` флаги — сходится с
`graft::layout`):

| Поле | Что |
|---|---|
| `+8`  | импл (`layout::desc_impl`) |
| `+32` | массив указателей на ДЕСКРИПТОРЫ переменных: сперва параметры, потом локали |
| `+44` | int: всего переменных (параметры + локали) |
| `+80` | флаги (`layout::desc_flags`) |
| `+88` | **uint8: сколько из них параметров** |

Скриптовая переменная в рантайме — **40 байт**, и движок её не «конструирует», а
**копирует шаблон из дескриптора**: `sub_1403663B0` строчками
`*(_OWORD*)(v14-40) = *(_OWORD*)v17; *(_OWORD*)(v14-24) = *(_OWORD*)(v17+16);
*(_QWORD*)(v14-8) = *(_QWORD*)(v17+32);` льёт 40 байт из `((void**)(desc+32))[i]` в
кадр потока (`thread+7248`, вершина в `thread+76`). Раскладка та же, что мы уже читаем
в `read_var`: значение `+0`, тег `+16` (проверено — `*(desc_var+16) & 0xF0000000`),
флаги `+20`; `+32`/`+34` — uint16 размерности статического массива.

**Следствие для graft: шаблон переменной изобретать не нужно — его несёт сама
вызываемая функция.** Чтобы позвать маршалируемый `proto`: взять `n = *(uint8*)(desc+88)`,
скопировать по 40 байт из `((void**)(desc+32))[i]`, положить значение в `+0` по тегу
`+16`, собрать массив указателей и звать импл.

#### Форм вызова ДВЕ, и перепутать их значит упасть

| Что за метод | Как зовётся | Приёмник |
|---|---|---|
| метод настоящего КЛАССА (`PlayerIdentity.GetPlainId`, наши нативы) | `impl(self, void*** args, void** ret)` | объект в rcx |
| статический (`EnScript.GetClassVar`, `Class.CastTo`) | `impl(void*** args, void** ret)` | нет |
| метод ТИПА-ЗНАЧЕНИЯ (`typename.Spawn`, `string.Substring`) | `impl(void*** args, void** ret)` | **первым в блоке** |

Видно прямо в сигнатурах декомпилированных имплов: `typename.Spawn` (`sub_140315FE0`) —
`f(a1, a2)`, где `**(*a1)[0]` это дескриптор класса, а `*a2` — переменная возврата;
`typename.GetModule` (`sub_140306040`) — `f(a1, a2)` с `***a1`; `EnScript.GetClassVar`
(`sub_140306130`) — `f(a1, a2)`, где `(*a1)[0..3]` четыре аргумента. Ни у одного нет
объекта в rcx.

Отсюда же и `desc+88` сходится с объявлением: у методов класса он равен числу
объявленных параметров, у методов типа-значения — на один больше (приёмник тоже
переменная блока). Измерено на живом движке: `string.Substring` 2 объявлено -> 3,
`typename.Spawn` 0 -> 1, `PlayerIdentity.GetPlainId` 0 -> 0, `EnScript.GetClassVar`
4 (static) -> 4.

Первая попытка звать всё трёхаргументной формой дала `0xC0000005`: движок прочитал наш
rcx как массив аргументов. Стоит помнить, что `+88` это не «сколько аргументов у
функции», а «сколько переменных в блоке».

Новые биты флагов функции (`+80`), из той же подготовки кадра:
`0x10` — у функции есть кадр переменных, `0x100000` — аргументы приходят сырым
значением (копируется только 8 байт в `+0`), `0x200000` — не доинициализировать локали.

Зачем это всё: почти весь «второй этаж» скриптового API — маршалируемый, а не нативный.
`typename.Spawn()` (создать любой скриптовый объект), `EnScript.GetClassVar(null, "g_Game", ...)`
(глобальная переменная, то есть корень объектного графа), `ScriptModule.CallFunction`
(позвать скриптовую функцию), `PlayerIdentity.GetPlainId()` — все `proto`, не `proto native`.
Один примитив открывает всё сразу.

### Что оказалось на живом движке (и чего не было в дизассемблере)

Разбор дал форму вызова, но три вещи выяснились только запуском.

**1. Блок аргументов — не массив, а СТРУКТУРА С ДВУМЯ МАССИВАМИ.**

```c
struct { void** values; void** vars; };   // rdx (или rcx у формы без объекта)
```

По `+0` имплы берут указатели на значения, по `+8` — на сами переменные, и пользуются
кто чем: `typename.Spawn` (`sub_140315FE0`) только первым, `EnScript.GetClassVar`
(`sub_140306130`) обоими — через аксессор `sub_1403672C0`, который буквально
`*(*(a1+8) + 8*i)`. Подать один голый массив значит уронить вторую половину функций.
Значение живёт в самой переменной по `+0`, поэтому у нас оба массива — один и тот же.

**2. Тип переменной движок берёт по полю `+24`, а не по тегу.**

```c
sub_140367280(var) = (*(void**)(var+24))[104][tag & 0xFFFFFFF]
```

Отсюда и правило «переменную не сочинять»: с верным тегом, но пустым `+24` разрешение
типа падает на `[rcx+0x68]`, где rcx = 0 (проверено). Переменной возврата дескриптор
функции не носит, поэтому шаблон для неё берётся у чужого параметра того же типа —
доноры перечислены в `INCLUDE/graft/callout.hpp`.

**3. `void` в объявлении параметра — это семейство `0x7`, а не ноль.**
Снято с дескриптора `EnScript.GetClassVar`: `p0=0x60000005 p1=0x50000003 p2=0x20000000
p3=0x70000004`. Означает «любой тип»: настоящую переменную движок собирает на месте
вызова по фактическому аргументу.

**4. Поле-вектор лежит в слоте ССЫЛКОЙ, а не значением.**

Адрес поля — `объект + база класса + 4 * слот`, и почти всё лежит в самом слоте: int,
float, bool значением, string и ссылка — указателем. Вектор ведёт себя ИНАЧЕ: в слоте
указатель на три float, а сам буфер — сразу за ним (замерено на живом объекте: слот
`…F9C0` содержал `…F9C8`). Двенадцать байт поверх слота убивают указатель, и падает не
тот, кто писал, а первое же ЧТЕНИЕ поля из скрипта. Буфер принадлежит объекту и живёт
столько же, считать на нём нечего — поэтому запись ЧЕРЕЗ указатель безопасна так же,
как в float. Реализация — `read_field`/`write_field` в `INCLUDE/graft/types.hpp`,
проверка на синтетическом объекте — `FieldSlots.*` в `tests/types_test.cpp`, на живом —
кейс `Fields_VectorThroughPointer`.

Про ЭЛЕМЕНТ контейнера это ничего не говорит: там раскладка своя (у `array<int>` шаг 4,
у `array<string>` — 8, то есть шаг равен размеру хранимого). Для `array<vector>` шаг
пока ВЗЯТ равным 12 по аналогии, а не замерен — замер делает кейс
`Array_VectorElementStride` (ищет второй элемент по сырому буферу и различает 8/12/16).

**Про саму GetClassVar** (проверено и из C++, и из скрипта):
- **код возврата врёт** — 0 даже на успешном чтении, при верном значении в out-аргументе;
- **глобальные переменные она не отдаёт** — `g_Game` даёт null и скрипту тоже. Поэтому
  корень объектного графа graft получает от мода вместе с тиком.

### Препроцессор в ванильных скриптах

1452 `#ifdef`, 346 `#ifndef`, 254 `#else`, 1798 `#endif` — и **ни одного составного
`#if`**. Условие любого объявления это конъюнкция простых «определён / не определён»,
поэтому разобрать его легко. А вот РАЗРЕШИТЬ нельзя: какие дефайны были у запущенной
игры, не говорит никто, кому можно верить.

Поэтому `graft apigen` запекает объединение всех веток, а не выбирает одну: методы,
поля и обе цепочки наследования (`class Man extends Person` против
`class Man extends EntityAI`). Чего в конкретной сборке нет, то просто не найдётся в
рантайме — и это дёшево, потому что поиск дескриптора прекращается после восьми
промахов (замер: 1.19 против 1.24 у обычного вызова, то есть добавленной цены нет).

Заодно нашлась потеря, к дефайнам отношения не имеющая: `class IEntity: Managed` —
двоеточие без пробела прилипало к имени, и класс отбрасывался ЦЕЛИКОМ. Вместе с IEntity
пропадали `GetOrigin`/`GetID`/`GetName` у каждой сущности мира. После правки разбор
даёт 6079 классов вместо 4959 и 3266 объявлений вместо 2950.
