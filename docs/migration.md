# Переход между версиями

Что менять в плагине при обновлении graft. Полный список изменений — в
[CHANGELOG.md](../CHANGELOG.md).

## 0.4.0 → 0.4.1

**Коротко:** плагин на 0.4.0 собирается без правок, а объявления для прежних привязок
генерируются те же. ABI 7 и LAYOUT 2 не изменились: ядро 0.4.1 грузит плагины 0.4.0, и
наоборот. Что делать дальше, зависит от того, что в плагине есть:

| В плагине | Что делать |
|---|---|
| только хуки, патчи, сканер, журнал — привязок к скрипту нет | ничего: собранная DLL работает с новым ядром, пересборка даёт тот же код |
| `proto native` без маршалинга, классы с полями | по желанию пересобрать: экземпляр класса ищется быстрее |
| `proto` — `graft::value`, `graft::param<"...">`, out-аргумент — или `bind.template_class` | **пересобрать**: исправления маршалинга живут в заголовках, замена `hid.dll` их не даст |

Проверено на DayZ 1.30.164.289 (сьюта `seraph::graft`). 0.4.0 проверялся на 1.29. Плагины
первой группы, QueuePriority и AS_MemoryLimits, собраны с 0.4.0 и с 0.4.1: секции DLL
совпали побайтно.

### Что сделать

1. Поднять тег в `CMakeLists.txt` мода:

   ```cmake
   graft_import(graft https://github.com/KRdayzmodding/KR_GRAFTED TAG v0.4.1)
   ```

2. Пересобрать плагин и заново упаковать мод — если он во второй или третьей группе таблицы.
3. Обновить ядро там, где запускается игра: `graft install <папка игры>`. Это
   необязательно, плагин 0.4.1 работает и со старым ядром. Новое ядро в 4.5 раза быстрее
   заводит экземпляр класса с полями на первом вызове: раньше на каждом новом объекте шёл
   системный вызов.

### Что починит пересборка

Касается тех, у кого есть маршалируемые нативы (`proto`): с `graft::value`,
`graft::param<"...">` или out-аргументом.

- **Поле объекта аргументом.** Вызов вида `obj.Describe(holder.m_Text)` в 0.4.0 читал
  тип не оттуда: строковое поле приезжало пустым, остальные — мусором. Теперь поле
  приезжает со своим типом, как в ванильный `Print`.
- **out в поле объекта.** `obj.Split(8, holder.m_A, holder.m_B)` в 0.4.0 писал 8 байт в
  4-байтовую ячейку поля и затирал соседнее поле. У последнего поля объекта запись уходила
  за его конец: порча кучи и падение сервера (0xC0000374). Теперь int, float и bool
  пишутся ровно 4 байтами, а переменную с флагом запрета записи (0x40) натив не трогает.
- **Методы шаблонного класса** (`bind.template_class`). Исключение или сбой в них в 0.4.0
  ронял сервер. Теперь они под той же защитой, что остальные нативы: сбой пишется в
  журнал, вызов возвращает значение по умолчанию.

### Новое: можно, но не обязательно

Старая запись работает везде. Ниже — как то же пишется короче.

#### Имя метода берётся из функции C++

```cpp
// 0.4.0
bind.class_<StringTable>("ExampleTable").method<&StringTable::Set>("Set");
bind.global<&Resettle>("Resettle", "slot, zone, player", "Переселить игрока в зону.");

// 0.4.1
bind.class_<StringTable>("ExampleTable").method<&StringTable::Set>();
bind.global<&Resettle>({.args = "slot, zone, player", .doc = "Переселить игрока в зону."});
```

Имя в скрипте — имя функции без класса и параметров шаблона. Другое имя задаётся явно:
`{.name = "Put"}`. Имена аргументов из C++ не достать, поэтому они по-прежнему строкой; без
них в объявлении будут `p0`, `p1`.

Учтите: теперь переименование функции в C++ переименовывает и натив в скрипте. Если
скриптовое имя — публичный API мода, задайте его через `.name`.

#### Новый класс: `graft::new_class` вместо `graft::fresh`

```cpp
// 0.4.0
struct StringTable {
    std::unordered_map<std::string, std::string> data;
    void Set(std::string k, std::string v);
};
bind.class_<StringTable>("ExampleTable", graft::fresh).method<&StringTable::Set>("Set");

// 0.4.1
struct StringTable : graft::new_class<"ExampleTable"> {
    std::unordered_map<std::string, std::string> data;
    void Set(std::string k, std::string v);
};
bind.class_<StringTable>().method<&StringTable::Set>();
```

Объявление то же: `class ExampleTable { ... }`. Что даёт `new_class`:

- имя класса записано в одном месте — в типе;
- база задаётся типом C++, и наследование настоящее (ниже);
- объект класса можно принять аргументом (ниже);
- из метода доступен сам скриптовый объект: `ptr`, `call()`, `field()`.

Своё поле `ptr` в такой структуре заводить нельзя: перед каждым вызовом graft пишет туда
скриптовый объект. Свои методы `call`, `field`, `has`, `proto` скроют одноимённые методы
базы. Если такие имена уже заняты — переименуйте их или оставьте `graft::fresh`.

#### Класс с базой

```cpp
struct Animal : graft::new_class<"MyAnimal"> {
    int legs = 4;
    int Legs() const { return legs; }
};

struct Dog : graft::new_class<"MyDog", Animal> {
    int barks = 0;
    int Bark() { return ++barks; }
};

GRAFT_BINDINGS("3_Game") {
    bind.class_<Animal>().method<&Animal::Legs>();
    bind.class_<Dog>().method<&Dog::Bark>();
}
```

```c
class MyAnimal
{
    proto native int Legs();
}

class MyDog : MyAnimal
{
    proto native int Bark();
}
```

На один скриптовый объект приходится один экземпляр C++. `Legs()`, позванный на объекте
`MyDog`, видит тот же `Dog`, с его полями. Скриптовый наследник (`class MyPuppy : MyDog`
в моде) получает экземпляр `Dog`: родство graft спрашивает у движка. Базой может быть и движковый класс:
`graft::new_class<"MyThing", graft::ref<"Managed">>`.

#### out-аргумент — обычной ссылкой

```cpp
// 0.4.0: out только через graft::value / graft::param
void Split(graft::f32 total, graft::param<"float">& left, graft::param<"float">& right);

// 0.4.1
void Split(graft::f32 total, graft::f32& left, graft::f32& right);
```

Объявление в обоих случаях `proto void Split(float p0, out float p1, out float p2)`.
Неконстантная ссылка на `bool`, `int`, `float` или `vector` сама делает натив
маршалируемым (`proto`). Строку через out вернуть нельзя, ею владеет движок:
`std::string&` даёт ошибку компиляции с объяснением. Строку возвращайте результатом.

#### Объект класса с полями аргументом

```cpp
int LegsOf(const Animal& animal);   // proto native int LegsOf(MyAnimal p0);
```

Натив получает тот же экземпляр, что видят методы этого объекта. Работает в `proto native`
и в `proto`. Принимается только константная ссылка: неконстантная означала бы out. `NULL`
вместо объекта — отказ в журнал, натив не выполняется.

### Изменилось поведение

- `graft::live_instances<C>()` считает и экземпляры наследников `C`.
- Сбой в методе шаблонного класса больше не роняет сервер (см. выше).

### Если вы пользовались `graft::detail`

Это не API, но на случай, если пользовались:

- убраны `typed_thunk` и `from_var`: методы шаблонных классов идут через тот же
  `marshal_thunk`, что и обычные;
- имя аргумента для объявления — `marshal_decl<A>` вместо `marshal_arg<A>::id` и `::value`;
- `marshal_thunk<C, F>::call` и `marshal_free_thunk<F>::call` принимают
  `script::arg_block*` вместо `void***`;
- `detail::instances<C>()` хранит `held` (экземпляр и его тип), а не сам `C`.

Живые экземпляры считайте через `graft::live_instances<C>()`.

### Известное на 1.30

Вызов движкового маршалируемого `proto` из C++ (`o.proto<...>()`, `type::try_proto`) на
1.30 возвращает пусто или ноль: красны кейсы `Out_MarshalledCallReturnsValue` и
`Tick_LoopProbe`. Они красны и на коде 0.4.0, причина не разобрана. Если плагин так
вызывает движок, проверьте это на своём сервере.
