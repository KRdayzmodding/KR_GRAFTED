# Доступ к коду движка: найти, позвать, перехватить

Справочник по трём заголовкам, которыми плагин дотягивается до самого движка, а не до
скриптового API: [`graft/scan.hpp`](../INCLUDE/graft/scan.hpp) — поиск,
[`graft/engine.hpp`](../INCLUDE/graft/engine.hpp) — врезка,
[`graft/world.hpp`](../INCLUDE/graft/world.hpp) — вход в объектный граф.

Нужно это там, где скриптового пути нет вовсе: у метода нет объявления `proto native`,
поведение зашито в C++ и меняется только перехватом, поле лежит в движковой структуре.
Если задача решается скриптовым API — решайте им: `ref::call` и `ref::proto` не зависят
от раскладки конкретной сборки игры, а всё ниже зависит.

**Зашитых адресов здесь нет и быть не должно.** Якорь — либо имя из публичного
script-API Enforce (оно переживает патч игры), либо имя класса из RTTI. Найденное
обязано пройти сверку байтовой сигнатурой: «нашлось не то» превращается в отказ, а не в
прыжок в середину чужой функции.

## Две конвенции возврата — главная ловушка

Возврат больше 8 байт (скриптовый `vector` — это 12) в `RAX` не влезает: под него
заводится буфер, адрес которого вызывающая сторона передаёт скрытым аргументом. **Куда
именно — зависит от того, к чему вы дотянулись**, и перепутанные регистры значат чтение
по мусору и запись результата поверх чужого объекта. Это `0xC0000005` на ровном месте.

| К чему дотянулись | Как звать | RCX | RDX |
|---|---|---|---|
| **зарегистрированный натив** (`RegisterMethod`, есть `proto native` в скрипте) | `ref::call<vector>(...)` | буфер | объект |
| **настоящий метод C++** (найден по RTTI/таблице, объявления в скрипте нет) | `scan::member_call<vector>(...)` | объект | буфер |

Это не вывод из документации, а снятое с движка. `IEntity.GetOrigin`, DayZDiag_x64 1.29,
импл найден по его же регистрации (`lea r9, [rip+impl]` перед `RegisterMethod`):

```
1402DD710  push rbx
1402DD712  sub  rsp, 20
1402DD716  mov  rbx, rcx        ; RCX запомнили...
1402DD719  test rdx, rdx        ; ...а на ноль проверяют RDX — объект приехал вторым
1402DD71C  jne  1402DD764
...
1402DD73D  mov  rax, rbx        ; и возвращают тот же RCX
1402DD748  movss [rbx],   xmm0  ; в него же пишут результат
1402DD754  movss [rbx+8], xmm0
```

И обратный случай — обычная функция-член, тоже из игры (`GetPosition`, +0x4A2F50):

```
1404A2F50  mov eax, [rcx+64]    ; RCX — это this: читают его поля
1404A2F53  mov [rdx], eax       ; RDX — буфер: в него пишут
...
1404A2F61  mov rax, rdx
```

Правило держит кейс `MemberCall.TwelveByteReturnRidesInTheSecondArgument`: сломается ABI
компилятора — покраснеет сьюта, а не сервер.

## Поиск: `scan.hpp`

### Секции образа

```cpp
std::vector<view> sections_of(void* module);
```

Секции загруженного модуля: байты, адрес и признак «исполняемая». Одна на всех — и хосту
для поиска регистрации, и плагину для чего угодно. Держите результат в статике: он не
меняется, а перечисление стоит прохода по заголовку PE.

```cpp
const std::vector<graft::scan::view>& sections() {
    static const auto s = graft::scan::sections_of(GetModuleHandleW(nullptr));
    return s;
}
```

`view` умеет искать внутри себя: `find_cstr(text)` — адрес целой C-строки (не хвоста
чужой), `find_lea(opcode, target)` — инструкцию `lea reg,[rip+d]`, указывающую на адрес,
`rel32_after/rel32_before(ea, span, opcode)` — цели переходов, `contains(ea)`.

### Таблица класса по имени из RTTI

```cpp
std::uintptr_t rtti_vtable(void* module, const char* mangled);
std::uintptr_t rtti_vtable(const std::vector<view>& sections,
                           std::uintptr_t image_base, const char* mangled);
```

Чистая механика MSVC, про DayZ не знает ничего. Так берётся класс, у которого нет ни
одного натива, — а от таблицы уже идут его методы.

```cpp
const std::uintptr_t vt = graft::scan::rtti_vtable(
    GetModuleHandleW(nullptr), ".?AVAIBehaviourGoToTarget@@");
```

Ноль — не нашли; это отказ, а не повод идти дальше по догадке.

> **Буква после `.?A` — это вид типа**, и перепутать её легко: `V` у `class`, `U` у
> `struct`, `W` у `enum`. Самый частый способ «ничего не найти».

Две вещи, из-за которых наивная реализация не находит ничего, — обе стоили отладки и обе
закрыты кейсами:

1. **Имя лежит в образе не один раз.** Первым совпадением почти всегда оказывается
   строковый литерал *того, кто ищет*: имя приезжает как `rtti_vtable(mod, ".?AVFoo@@")`,
   и своя же копия строки лежит в `.rdata` вызывающего. Перебираются все вхождения.
2. **Локатор узнаётся по себе самому.** У x64-версии есть поле `pSelf` со своим же RVA —
   случайный `dword`, равный RVA имени, такую сверку не проходит.

Дескриптор типа при этом лежит в **записываемой** секции (у него поле-кэш имени), а
локатор и таблица — в read-only. Отсеять полсотни мегабайт `.data` по правам страниц
нельзя: поиск сломается.

### Длина таблицы

```cpp
std::size_t vtable_slots(void* const* vt);
```

Подряд идущие адреса машинного кода, с проверкой читаемости каждого слота. Длину таблицы
никто не хранит, поэтому она считается; потолок — 256 слотов, чтобы не уехать в соседние
данные, если `.rdata` продолжается такими же указателями.

### Сигнатуры

```cpp
bool matches(std::uintptr_t ea, std::span<const int> sig);
bool matches(std::uintptr_t ea, std::initializer_list<int> sig);
template <name_t S> inline constexpr auto sig;   // scan::sig<"48 89 ?? 57">
```

Сверка байт по адресу; элемент `< 0` — «любой байт» там, где в инструкцию запечено
смещение поля или регистр, выбранный компилятором игры. Нечитаемый адрес — `false`, а не
падение.

Две формы, и первая предпочтительнее:

```cpp
scan::matches(fn, scan::sig<"48 89 5C 24 ?? 57">);   // разбирается на КОМПИЛЯЦИИ
scan::matches(fn, {0x48, 0x89, 0x5C, 0x24, -1, 0x57});
```

Строка копируется из отладчика как есть; лишние пробелы законны, `?` и `??` — оба
джокер, регистр цифр не важен. Опечатка (`"4"` вместо `"48"`, `???`, посторонний символ)
— **ошибка сборки**, а не сигнатура, которая молча ничего не находит и отлаживается уже
на живом сервере. Список чисел остаётся для случая, когда байты приходят из переменной.

`begins_with(ea, span<const uint8_t>)` — то же без джокеров, для готового блока байт.

### Цели переходов

```cpp
std::vector<std::uintptr_t> rel32_targets(const std::vector<view>& sections,
                                          std::uintptr_t ea, std::size_t span,
                                          std::uint8_t opcode = 0xE8);
```

Куда зовёт функция (`0xE8`) и чем кончается (`0xE9` — хвостовой `jmp`). Мусорные цели
отброшены: байт опкода встречается и внутри чужого смещения, а настоящая цель обязана
лежать в исполняемой секции. Окно кончается ровно там, где сказано, — иначе разбор одной
функции цепляет соседнюю.

Рядом: `first_call(sections, fn, span)` — цель первого вызова, `disp32_of` / `disp8_of` —
смещение из инструкции с заданным опкодом (так достаются и поля структур, и адреса
глобалей).

### Чтение по чужому адресу

```cpp
bool readable(const void* p, std::size_t n);
bool is_code(const void* p);
```

Спрашивается у системы, а не пробным чтением под SEH: движок ставит свой фильтр
исключений и рапортует о падении раньше, чем сработал бы `__except`.

> `scan::readable` **выравнивания не требует** — адрес внутри функции ничем не выровнен.
> Рядом живёт `script::detail::readable`, который сперва проверяет «похоже ли это вообще
> на указатель», включая кратность восьми: там это правильно (проверяется *значение
> поля*), здесь — нет. Отсюда две функции при одной проверке страницы.

### Вызов настоящего метода C++

```cpp
template <class R, class... A>
R member_call(void* fn, void* self, A... args);
```

Для методов, найденных по RTTI. Скрытый буфер под большой возврат кладётся вторым, после
`this` — см. [таблицу конвенций](#две-конвенции-возврата--главная-ловушка). Для возврата,
влезающего в регистр, это обычный fastcall; решает концепт `returned_in_register`.

## Врезка: `engine.hpp`

```cpp
bool hook(void* target, void* detour, void** original);
bool unhook(void* target);

template <class F> bool hook(F target, F detour, F* original);   // без приведений
template <class F> bool unhook(F target);
```

```cpp
graft::hook(&Engine_Foo, &my_foo, &g_original);
```

`original` получает адрес **трамплина**: оригинал зовут через него, а не по `target` — по
`target` теперь лежит переход к детуру. Типы цели, детура и оригинала в шаблонной форме
обязаны совпасть; иначе кадр вызова разъедется молча.

**Почему это сервис хоста, а не библиотека в плагине.** Две механики врезки в одном
процессе друг о друге не знают: у каждой свой пул трамплинов и свой список целей. Пока
цели разные — сходит с рук; как только двум плагинам понадобится одна функция, второй
перепишет пролог, в котором уже стоит чужой переход, и трамплин первого поведёт в
середину инструкции. Механика одна на процесс, и повторная врезка в занятую цель —
честный отказ (кейс `Hook.RefusesToHookTheSameTargetTwice`).

Список занятых целей ведёт **сам хост**, а не библиотека под ним: у safetyhook такого
списка нет вовсе — он примет вторую врезку в ту же функцию и построит цепочку, которую
снятие в неверном порядке порвёт молча. Это ещё одна причина не заводить свою копию
плагину: отказ живёт в хосте, и мимо хоста его не получить.

### Пачкой

```cpp
using hook_request = graft_hook_request;   // { target, detour, original }

bool hook_all(std::span<const hook_request> all);
bool hook_all(std::initializer_list<hook_request> all);
template <class F> hook_request hooked(F target, F detour, F* original);
```

```cpp
graft::hook_all({graft::hooked(&Engine_Foo, &my_foo, &g_foo),
                 graft::hooked(&Engine_Bar, &my_bar, &g_bar)});
```

Пачка встаёт **целиком либо не встаёт вовсе**: половина врезок — это состояние, в котором
мод уже сломан, но ещё считает себя живым. Создание разбирает пролог и строит трамплин,
ничего не трогая; патч идёт вторым проходом, и если хоть одна заявка не создалась, до
патча дело не доходит.

Дешевле поштучной установки пачка **не становится**: сама врезка стоит сотые доли
миллисекунды (`Hook.InstallCostIsMeasured`).

### Когда врезка безопасна

Контракт один, и он не пожелание: **врезку ставят из точки входа плагина**. Не с тика, не
по событию в игре, не по команде из скрипта.

Причина в том, как патчится пролог. Переписываются первые байты функции, а внутри них есть
границы инструкций. Поток, снятый планировщиком ровно на такой границе, после пробуждения
продолжит с середины уже другой инструкции: сбоя у него нет, он спит, и ловушка safetyhook
на правах страницы его не видит. На стресс-кейсе это выглядит так:

```
[СБОЙ] code=C000001D rip=...51F1 ... answer=...51F0
```

Недопустимая инструкция, `rip` на один байт внутри цели.

Закрыть это можно только остановкой всех потоков процесса на время патча. В graft такой
остановки нет и не будет: `SuspendThread` останавливает поток внутри любого замка, включая
кучный, а под остановкой нужен именно он — взаимная блокировка неустранима, и цена ей
вечно висящий сервер вместо редкого падения. Вдобавок этот вызов в игровом процессе
выглядит ровно так, как выглядит вмешательство в чужую память, и в дереве его нет ни
одного.

Вместо остановки — условие, при котором гонки **не существует**, и graft ему удовлетворяет
устройством, а не дисциплиной. `hid.dll` тянется таблицей импорта exe до `main()`. В
`DllMain` заводится поток, он делает скан, ставит свои врезки и тут же зовёт точки входа
всех плагинов. Движок к этому моменту не создал ещё ни одного своего потока.

**Снятая врезка не разрушается, а уходит в отставку.** Патч переводит поток, стоявший
внутри пролога, в трамплин — это делает сам safetyhook. Освободить трамплин сразу после
снятия значит убрать память из-под того, кто в ней исполняется. Трамплины снятых врезок
живут до конца процесса: десятки байт на снятие, а снимают редко.

**Снятая врезка не оставляет за собой ничего, что съест чужой сбой потом.** В апстриме
оставляла: список отравленных страниц там не чистится, а обработчик решает по признаку
«страница когда-то была нашей», и настоящий сбой на ней уходил в вечный повтор вместо
падения с дампом. Правится заплаткой на этапе конфигурации, см.
[SRC/patches/README.md](../SRC/patches/README.md): признак заменён на проверяемый — пока
окно патча открыто, всё как в апстриме, а после закрытия «продолжай» отвечается, только
если права страницы подтверждают, что повтор пройдёт. Сторожит кейс
`Hook.RemovedHookLeavesNothingThatSwallowsFaults`.

**Детур можно защитить так же, как натив:**

```cpp
graft::hook<&my_foo>(&Engine_Foo, &g_orig);   // падение в детуре отменит вызов, не игру
graft::hook(&Engine_Foo, &my_foo, &g_orig);   // как было, под свою ответственность
```

Голая форма оставлена намеренно: детур, который обязан досылать управление оригиналу при
любом исходе, раскрутку пережить не может, и решать это вправе только его автор.

### Чего делать нельзя

> **Не вешайте хук на функцию, которую зовут из сотен мест с разными аргументами.**
> Детур на C++ считает регистры `xmm` своими, и чужой вызов с вещественным аргументом
> уезжает в движок испорченным. Это стоило трёх падений сервера. Если место вызова
> известно — перенаправляйте **его**, а не функцию: так сделан кадр
> ([`SRC/graft/frame.cpp`](../SRC/graft/frame.cpp), разбор — у `scan::frame_entry`).

Врезки — работа старта, а не игрового цикла: сама по себе она стоит десятки миллисекунд,
а вызов после неё — один `jmp`.

## Объектный граф: `world.hpp`

```cpp
template <script_class T> vector position(T entity);
template <script_class T> std::expected<vector, miss> try_position(T entity);
```

Позиция сущности мира — движковый `IEntity.GetOrigin()`. Он есть у любой сущности:
объявлен на базовом классе, а поиск метода идёт с обходом базовых. Скриптовый
`Object.GetPosition()` отдаёт то же значение (сверяется в игре, кейс
`Entity_MethodsFromCpp`).

```cpp
const graft::vector at = graft::position(player);
```

Без движка — нули у `position` и промах в типе у `try_position`, но не падение.

Рядом в том же заголовке: `game()` — корень объектного графа, `spawn<T>()` — движковый
`typename.Spawn`, `borrowed<T>` — чужой объект с проверкой, что по адресу всё ещё объект
того же класса, `try_script_var` — переменная по имени руками движка.

## Сквозной пример

Так устроен реальный плагин: от имени класса до вызова метода, без единого зашитого
адреса.

```cpp
#include "graft/native.hpp"
#include "graft/scan.hpp"

namespace {

const std::vector<graft::scan::view>& sections() {
    static const auto s = graft::scan::sections_of(GetModuleHandleW(nullptr));
    return s;
}

bool resolve() {
    // 1. Класс -> его таблица.
    const std::uintptr_t vt =
        graft::scan::rtti_vtable(GetModuleHandleW(nullptr), ".?AVAIBehaviourGoToTarget@@");
    if (!vt || graft::scan::vtable_slots(reinterpret_cast<void* const*>(vt)) <= 10) {
        return false;
    }

    // 2. Виртуальный метод -> его тело. У слота бывает переходник, поэтому берём цель
    //    хвостового jmp, а не сам слот.
    std::uintptr_t entry = 0;
    std::memcpy(&entry, reinterpret_cast<const void*>(vt + 10 * 8), sizeof entry);

    for (std::uintptr_t body : graft::scan::rel32_targets(sections(), entry, 0x60, 0xE9)) {
        // 3. Сверка: кандидат становится ответом только когда совпал пролог.
        if (!graft::scan::matches(body, graft::scan::sig<"48 89 5C 24 10 57 48 83 EC 20">)) {
            continue;
        }
        // 4. Его собственные вызовы — то, ради чего всё и затевалось.
        for (std::uintptr_t callee : graft::scan::rel32_targets(sections(), body, 0x140)) {
            ...
        }
        return true;
    }
    return false;
}

}  // namespace
```

Дальше найденное либо зовётся (`scan::member_call<R>(fn, self, args...)` для метода
класса, обычный `reinterpret_cast` к `__fastcall` — для свободной функции), либо
перехватывается (`graft::hook`). Результат поиска мемоизируйте: он не меняется за жизнь
процесса.

## Цена

Замеры печатает сама сьюта (`graft_tests.exe`), поэтому числа не устаревают молча.

| Что | Цена | Когда платится |
|---|---|---|
| вызов после врезки | один `jmp` | — |
| установка врезки, по одной | ~40 мс | старт |
| установка врезки, пачкой | ~40 мс **на всю пачку** | старт |
| `rtti_vtable` на образе игры | ~3 мс (~20 ГБ/с × 61 МБ данных) | один раз, мемоизируйте |
| `matches`, `rel32_targets` на окне 0x140 | наносекунды | разбор функции |
| `member_call`, `position` | как обычный вызов натива | — |

Ничего из этого не место на горячем пути. Разбор — на старте (или лениво, но один раз),
дальше в руках уже готовые адреса.
