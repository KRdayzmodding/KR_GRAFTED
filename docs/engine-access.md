# Доступ к коду движка: найти, позвать, перехватить

Справочник по трём заголовкам, которыми плагин дотягивается до самого движка, а не до
скриптового API: [`graft/scan.hpp`](../INCLUDE/graft/scan.hpp) — поиск,
[`graft/engine.hpp`](../INCLUDE/graft/engine.hpp) — врезка,
[`graft/world.hpp`](../INCLUDE/graft/world.hpp) — вход в объектный граф.

Нужно это там, где скриптового пути нет вовсе: у метода нет объявления `proto native`,
поведение зашито в C++ и меняется только перехватом, поле лежит в движковой структуре.
Если задача решается скриптовым API — решайте им: `ref::call` и `ref::proto` не зависят
от раскладки конкретной сборки игры, а всё ниже зависит.

**Зашитых адресов здесь нет и быть не должно.** Якорь — либо имя из публичного
script-API Enforce (оно переживает патч игры), либо имя класса из RTTI. Найденное
обязано пройти сверку сигнатурой — и сигнатуры пишутся строчками ассемблера, теми самыми,
что показывает отладчик. «Нашлось не то» превращается в отказ, а не в прыжок в середину
чужой функции.

## Две конвенции возврата — главная ловушка

Возврат больше 8 байт (скриптовый `vector` — это 12) в `RAX` не влезает: под него
заводится буфер, адрес которого вызывающая сторона передаёт скрытым аргументом. **Куда
именно — зависит от того, как собрана функция**, и перепутанные регистры значат чтение
по мусору и запись результата поверх чужого объекта. Это `0xC0000005` на ровном месте.

| Как собрана | Где встречается | RCX | RDX |
|---|---|---|---|
| **функция-член C++** | обычный `proto native` метода (`Object.GetPosition`, флаги `0xa28`); метод, найденный по RTTI | объект | буфер |
| **свободная функция** | `proto native external` (`IEntity.GetOrigin`, флаги `0x4a28`); глобальный натив | буфер | объект |

Нативы различает бит `0x4000` дескриптора (`layout::flag_external`), и `ref::call` /
`try_call` выбирают форму по нему сами — для `vector` и для любого другого возврата
через буфер. Руками форму выбирают только для метода, найденного по RTTI: это всегда
функция-член, и зовётся она `scan::member_call`.

Тем же битом движок выбирает, как звать **ваши** нативы. У метода, привязанного через
`bind.class_<C>().method<...>`, флаги те же `0xa28`, поэтому трамплин с возвратом
`vector` принимает буфер вторым, как функция-член; глобальный и статический натив — как
свободная функция.

Это не вывод из документации, а снятое с движка. `IEntity.GetOrigin`, DayZDiag_x64 1.29,
импл найден по его же регистрации (`lea r9, [rip+impl]` перед `RegisterMethod`):

```
1402DD710  push rbx
1402DD712  sub  rsp, 20
1402DD716  mov  rbx, rcx        ; RCX запомнили...
1402DD719  test rdx, rdx        ; ...а на ноль проверяют RDX — объект приехал вторым
1402DD71C  jne  1402DD764
...
1402DD73D  mov  rax, rbx        ; и возвращают тот же RCX
1402DD748  movss [rbx],   xmm0  ; в него же пишут результат
1402DD754  movss [rbx+8], xmm0
```

И обратный случай — `Object.GetPosition`, импл из его же дескриптора (+0x4A2F50):

```
1404A2F50  mov eax, [rcx+64]    ; RCX — это this: читают его поля
1404A2F53  mov [rdx], eax       ; RDX — буфер: в него пишут
...
1404A2F61  mov rax, rdx
```

Флаги сняты в игре кейсом `Diag_MethodFlags`. Правило держат юнит-тесты
`MemberCall.TwelveByteReturnRidesInTheSecondArgument`, `NativeCall.*` (вызов натива обеих
форм) и `MemberVectorNative.*` (свой трамплин глазами движка), а в игре — кейсы
`Entity_VectorNativesFromCpp` и `Fields_VectorThroughPointer`: сломается ABI
компилятора — покраснеет сьюта, а не сервер.

## Поиск: `scan.hpp`

### Если не нашлось

Всякий поиск отвечает `std::expected<T, graft::miss>`: находка или причина отказа. Нулевого
адреса в роли «нет» нигде нет: его можно не проверить, а выглядит он как ответ.

| Причина | Что случилось | Что делать |
|---|---|---|
| `miss::not_found` | такого нет: после патча игры маяк пропал или сменил форму | открыть функцию в IDA и сверить с листингом |
| `miss::ambiguous` | таких несколько, и выбирать из них нельзя: маяк раздвоился | искать маяк точнее |
| `miss::unreadable` | по адресу нечего читать: он не из образа или мусорный | искать, откуда взялся адрес |

`graft::to_string(miss)` — причина словами, для журнала. Не нашлось — это «нет», а не повод
взять ближайшее подходящее: плагин выключает свою ветку и пишет причину в журнал. Цепочка
поисков передаёт отказ дальше как есть, и причина доезжает до журнала первой:

```cpp
std::expected<graft::scan::found, graft::miss> find_field() {
    const auto fn = graft::scan::function_referencing("текст ассерта");
    if (!fn) {
        return std::unexpected(fn.error());
    }
    return graft::scan::find_in_function(*fn, listing);
}
```

Коллекция (`rip_refs`, `rel32_targets`) в этом смысле не отказывает: «ничего» — пустой
`std::vector`. Предикат (`matches`, `is_code`, `readable`) — `bool`: у вопроса «ровно это?»
два ответа, и причина третьего ему не нужна.

**Окно в байтах — это число, которое кто-то должен знать.** «Искать в первых N байтах»
значит гадать N: мало — не дотянешься, много — окно перелезет в соседнюю функцию и
подхватит чужое. Поэтому в теле функции ищут без числа — `find_in_function` берёт конец
из таблиц раскрутки (`.pdata`). Окно задаётся только там, где границ нет вовсе: у куска
образа, у места вызова, у переходника без записи раскрутки. Там оно — число вызывающего:
безымянного дефолта у `calls_after`, `calls_before` и `first_call` нет, а в вашем коде
оно должно быть именованной константой с причиной рядом.

### Секции образа

```cpp
const std::vector<view>& image();                    // образ игры
std::vector<view>        sections_of(void* module);  // любой другой модуль
```

Секции загруженного образа: байты, адрес и признак «исполняемая». Одна на всех — и хосту
для поиска регистрации, и плагину для чего угодно.

`image()` — образ игры, главный модуль процесса, в котором живёт движок. Плагину почти
всегда нужен он, и ни модуль у системы брать не нужно, ни держать результат в своей
статике: секции считаются при первом обращении и дальше не меняются, ссылка живёт до конца
процесса. `sections_of(module)` — для чужого модуля (другой DLL); результат такого вызова
держите сами: перечисление стоит прохода по заголовку PE.

```cpp
const auto& sections = graft::scan::image();
```

`view` умеет искать внутри себя: `find_cstr(text)` — адрес целой C-строки (не хвоста
чужой), `find_rip(insn, target)` — инструкцию, которая через `rip` смотрит на адрес,
`find(ea, span, sig)` — сигнатуру в окне (все три — `std::expected`),
`rel32_after/rel32_before(ea, span, opcode)` — цели переходов, `contains(ea)`.

### Функция по строке-маяку

```cpp
std::expected<std::uintptr_t, miss> function_referencing(const char* text);   // по образу игры
std::expected<std::uintptr_t, miss> function_referencing(const std::vector<view>& sections,
                                                         const char* text);
std::vector<std::uintptr_t> rip_refs(const std::vector<view>& sections, const char* text,
                                     pattern_view insn);
std::expected<std::uintptr_t, miss> function_start(std::uintptr_t ea);
```

Для кода, у которого есть строка — текст ассерта, формат журнала, — но нет натива.
`function_referencing` отдаёт начало функции, которая берёт адрес ровно этой C-строки
(`lea reg,[rip+строка]`). Нет такой — `not_found`; на строку ссылаются РАЗНЫЕ функции —
`ambiguous`: угадывать из двух нельзя. Так хост находит проверку линковки модуля — по строке
`Method not linked '%s.%s'`.

Под ней две вещи, которые нужны и сами по себе: `rip_refs` — все места, где инструкция вида
`insn` смотрит на строку через `rip`, и `function_start` — начало функции, в которой лежит
адрес, по таблицам раскрутки `.pdata`. Записи идут сцепленными: у куска, который компилятор
вынес из функции, запись своя, и без сцепки «началом» оказался бы он. У адреса записи нет
(не код или лист без кадра) — `not_found`.

### Таблица класса по имени из RTTI

```cpp
std::expected<std::uintptr_t, miss> rtti_vtable(const char* mangled);   // по образу игры
std::expected<std::uintptr_t, miss> rtti_vtable(void* module, const char* mangled);
std::expected<std::uintptr_t, miss> rtti_vtable(const std::vector<view>& sections,
                                                std::uintptr_t image_base, const char* mangled);
```

Чистая механика MSVC, про DayZ не знает ничего. Так берётся класс, у которого нет ни
одного натива, — а от таблицы уже идут его методы.

```cpp
const auto vt = graft::scan::rtti_vtable(".?AVAIBehaviourGoToTarget@@");
```

Не нашли — `not_found`; это отказ, а не повод идти дальше по догадке.

> **Буква после `.?A` — это вид типа**, и перепутать её легко: `V` у `class`, `U` у
> `struct`, `W` у `enum`. Самый частый способ «ничего не найти».

Две вещи, из-за которых наивная реализация не находит ничего, — обе стоили отладки и обе
закрыты кейсами:

1. **Имя лежит в образе не один раз.** Первым совпадением почти всегда оказывается
   строковый литерал *того, кто ищет*: имя приезжает как `rtti_vtable(mod, ".?AVFoo@@")`,
   и своя же копия строки лежит в `.rdata` вызывающего. Перебираются все вхождения.
2. **Локатор узнаётся по себе самому.** У x64-версии есть поле `pSelf` со своим же RVA —
   случайный `dword`, равный RVA имени, такую сверку не проходит.

Дескриптор типа при этом лежит в **записываемой** секции (у него поле-кэш имени), а
локатор и таблица — в read-only. Отсеять полсотни мегабайт `.data` по правам страниц
нельзя: поиск сломается.

### Длина таблицы

```cpp
std::size_t vtable_slots(void* const* vt);
```

Подряд идущие адреса машинного кода, с проверкой читаемости каждого слота. Длину таблицы
никто не хранит, поэтому она считается; потолок — 256 слотов, чтобы не уехать в соседние
данные, если `.rdata` продолжается такими же указателями.

### Сигнатуры

```cpp
template <name_t S> inline constexpr auto code;  // строчками ассемблера (graft/asm.hpp)
template <name_t S> inline constexpr auto sig;   // байтами: scan::sig<"48 8B 81 [disp32]">

bool matches(std::uintptr_t ea, pattern_view sig);          // на этом адресе — ровно это?
struct found { std::uintptr_t site; std::int64_t value; };
std::expected<found, miss> find(std::uintptr_t ea, std::size_t span, pattern_view sig,
                                unsigned nth = 1);          // в окне чужой памяти
std::expected<found, miss> find_in_function(std::uintptr_t ea, pattern_view sig,
                                            unsigned nth = 1);  // до конца функции, без окна
// и то же по байтам секции — у неё они уже есть:
std::expected<found, miss> view::find(std::uintptr_t ea, std::size_t span, pattern_view sig,
                                      unsigned nth = 1) const;
std::expected<std::uintptr_t, miss> view::find_rip(pattern_view insn, std::uintptr_t target,
                                                   std::uintptr_t from = 0) const;
```

> **Внутри секции ищите `view::find`, а не свободную `find`.** Свободная спрашивает у
> системы, отображена ли страница, — ей передают адрес чужой памяти. У секции байты уже
> есть, а `base` у неё бывает и синтетическим (так собраны фикстуры сьюты), и тогда
> свободная честно отвечает «адрес не читается». На этом спотыкались обе первые попытки
> перевода — оба раза поймала сьюта.

Две записи одного и того же, и тип у них один — `pattern`. Выбор между ними — не вкусовщина,
а ответ на вопрос «что с этим будут делать»:

- **`scan::code`** — то, что читает человек, когда игру пропатчили: открыл функцию в IDA и
  сравнил листинг с исходником строка в строку. Так пишутся сигнатуры в коде.
- **`scan::sig`** — байты как измерение: «вот что лежало в образе той сборки». Так пишутся
  золотые таблицы в тестах, которыми сверяется первое.

#### Строчками ассемблера: `scan::code`

Подключается отдельно — `#include "graft/asm.hpp"`: `scan.hpp` кодировщик не тянет.

```cpp
constexpr auto prologue = scan::code<R"(
    mov  [rsp+8],rbx
    push rdi
    sub  rsp,20h
    mov  rbx,rcx
)">;
constexpr auto field = scan::code<"mov rax,[rcx+disp32]">;
```

Кодируется на компиляции, байт в байт; `disp8`/`disp32`/`imm8`/`imm32` на месте операнда —
та же дырка, что и в байтовой записи ниже. Мнемоники и регистры строчными, как их
печатает отладчик. Незнакомая инструкция или форма — **ошибка сборки с текстом**, а не молча
неверный байт; кодировщик знает ровно то, что встречается в разобранных функциях движка
(список — в шапке [`graft/asm.hpp`](../INCLUDE/graft/asm.hpp)).

**`reg64` — любой регистр.** На месте приёмника или источника пишется `reg64`, и тогда
отпускаются поле reg в `modrm` и бит R в префиксе REX — находятся и `rax..rdi`, и `r8..r15`:

```cpp
constexpr auto rip_lea = scan::code<"lea reg64,[rip+disp32]">;  // 48&FB 8D 05&C7 + дырка
```

Только 64-битный и только не в адресе. `reg32` — ошибка сборки, и не из лени: без `REX.W`
префикс у `r8d..r15d` появляется, а у `eax..edi` нет, то есть **длина инструкции разная**, и
одной сигнатурой оба случая не накрыть.

**`db` — сырые байты, и без него нельзя.** Строчка ассемблера не определяет байты
однозначно, и на коде движка это не теория: `push rbp` бывает `55`, а бывает `40 55` — с
лишним префиксом REX, который MSVC в кадровых функциях пишет. А ещё сигнатура может
намеренно **обрываться посреди инструкции**: в `mov rbx,[rcx+2B8h]` сверяются первые четыре
байта, потому что смещение `2B8h` — как раз то, что патч игры сдвигает. Ни то, ни другое
мнемоникой не выражается:

```cpp
    db   40                 ; лишний REX: так MSVC пишет push rbp в кадровой функции
    push rbp
    db   48 8B 99 B8        ; обрывок mov rbx,[rcx+2B8h]
```

Строчка с `db` в листинге сразу видна как «здесь сверяются байты, а не инструкция».

#### Байтами: `scan::sig`

Строка, скопированная из отладчика. Три вида токена, и больше никаких:

| Токен | Что значит |
|---|---|
| `48` | байт как есть |
| `??`, `?` | любой байт: там регистр или смещение, которое сверять нечем |
| `05&C7` | **часть байта**: сверяются биты маски, остальные любые. Так пишется «поле reg в modrm любое, а mod и rm вот такие» |
| `[disp32]` | **дырка**: столько бит любых — и это ответ. Слово в скобках для читателя, парсер берёт из него только число — ширину в битах: `[disp32]`, `[imm32]` и `[32]` — одно и то же, `[disp8]` — дырка в байт |

Маска — не украшение. Целиком сверить байт `modrm` нельзя (регистр-приёмник выбирает
компилятор игры), целиком отпустить его (`??`) нельзя тем более: под джокер подойдёт другая
форма адресации, а проверяем мы именно её. Пока маски не было, каждое место, которому она
нужна, писало свой цикл по байтам.

```cpp
constexpr auto prologue = scan::sig<"48 89 5C 24 ?? 57">;   // mov [rsp+?],rbx; push rdi
constexpr auto field    = scan::sig<"48 8B 81 [disp32]">;   // mov rax,[rcx+disp32]

if (!scan::matches(fn, prologue)) { return; }                 // тот ли это код
const auto at = scan::find_in_function(fn, field);            // где и что в дырке
if (at) { offsets.field = static_cast<unsigned>(at->value); }
```

`matches` сверяет по точному адресу, `find` ищет `nth`-е вхождение в `[ea, ea+span)` и
отдаёт адрес инструкции вместе с содержимым дырки. `find_in_function` — то же от `ea` и до
конца функции, в которой он лежит: конец берётся из `.pdata`, числа в вызове нет. Холодный
хвост, который компилятор вынес из функции, — отдельный кусок со своей записью, и окно
кончается на его краю. У адреса записи раскрутки нет — `not_found`: конца функции тут не
определить, а окно с потолка брать нельзя.

Нечитаемый адрес — `unreadable`, а не падение: кандидат мог приехать из мусорного смещения,
и «читать нечего» — не то же самое, что «искомого в памяти нет» (`not_found`). Дырка читается
**со знаком**, как её понимает процессор: `disp8` `0x80` — это −128, а не +128.

Строка разбирается на **компиляции**: лишние пробелы законны, регистр цифр не важен, а
опечатка (`"4"` вместо `"48"`, `???`, `[disp]` без ширины, две дырки) — ошибка сборки, а не
сигнатура, которая молча ничего не находит и отлаживается уже на живом сервере.

> Ширина смещения живёт в сигнатуре, а не в имени функции. Раньше их было две —
> `disp8_of` и `disp32_of`, — а какая нужна, было написано в комментарии рядом с опкодом:
> два места, которые обязаны совпасть, и расхождение не заметил бы ни компилятор, ни тест
> (код прочитал бы четыре байта там, где лежит один). Сличать теперь нечего.

### Цели переходов

```cpp
std::vector<std::uintptr_t> rel32_targets(const std::vector<view>& sections,
                                          std::uintptr_t ea, std::size_t span,
                                          std::uint8_t opcode = 0xE8);
```

Куда зовёт функция (`0xE8`) и чем кончается (`0xE9` — хвостовой `jmp`). Мусорные цели
отброшены: байт опкода встречается и внутри чужого смещения, а настоящая цель обязана
лежать в исполняемой секции. Окно кончается ровно там, где сказано, — иначе разбор одной
функции цепляет соседнюю.

Рядом: `first_call(sections, fn, span)` — цель первого вызова в окне `span`; вызова с целью
в исполняемой секции нет — `not_found`. Смещения полей структур и адреса глобалей достаются
из тех же байт — дыркой в сигнатуре, см. [Сигнатуры](#сигнатуры).

`view::find_rip(insn, target)` — адрес инструкции, которая через `rip` ссылается на `target`
(`lea reg,[rip+d]`, `mov [rip+d],reg` — любая); следующую ссылку ищут с `from`, больше нет —
`not_found`. Сигнатура берётся **целиком**, вместе с дыркой под смещение: `rip` смотрит за
конец инструкции, поэтому нужна и её длина. Это единственная реализация такого поиска на
весь проект.

### Чтение по чужому адресу

```cpp
bool readable(const void* p, std::size_t n);
bool is_code(const void* p);
```

Спрашивается у системы, а не пробным чтением под SEH: движок ставит свой фильтр
исключений и рапортует о падении раньше, чем сработал бы `__except`.

> `scan::readable` **выравнивания не требует** — адрес внутри функции ничем не выровнен.
> Рядом живёт `script::detail::readable`, который сперва проверяет «похоже ли это вообще
> на указатель», включая кратность восьми: там это правильно (проверяется *значение
> поля*), здесь — нет. Отсюда две функции при одной проверке страницы.

### Вызов настоящего метода C++

```cpp
template <class R, class... A>
R member_call(void* fn, void* self, A... args);
```

Для методов, найденных по RTTI (натив форму выбирает сам, его зовут через `ref::call`).
Скрытый буфер под большой возврат кладётся вторым, после `this` — см.
[таблицу конвенций](#две-конвенции-возврата--главная-ловушка). Для возврата, влезающего
в регистр, это обычный fastcall; решает концепт `returned_in_register`.

## Врезка: `engine.hpp`

```cpp
bool hook(void* target, void* detour, void** original);
bool unhook(void* target);

template <class F> bool hook(F target, F detour, F* original);   // без приведений
template <class F> bool unhook(F target);
```

```cpp
graft::hook(&Engine_Foo, &my_foo, &g_original);
```

`original` получает адрес **трамплина**: оригинал зовут через него, а не по `target` — по
`target` теперь лежит переход к детуру. Типы цели, детура и оригинала в шаблонной форме
обязаны совпасть; иначе кадр вызова разъедется молча.

**Почему это сервис хоста, а не библиотека в плагине.** Две механики врезки в одном
процессе друг о друге не знают: у каждой свой пул трамплинов и свой список целей. Пока
цели разные — сходит с рук; как только двум плагинам понадобится одна функция, второй
перепишет пролог, в котором уже стоит чужой переход, и трамплин первого поведёт в
середину инструкции. Механика одна на процесс, и повторная врезка в занятую цель —
честный отказ (кейс `Hook.RefusesToHookTheSameTargetTwice`).

Список занятых целей ведёт **сам хост**, а не библиотека под ним: у safetyhook такого
списка нет вовсе — он примет вторую врезку в ту же функцию и построит цепочку, которую
снятие в неверном порядке порвёт молча. Это ещё одна причина не заводить свою копию
плагину: отказ живёт в хосте, и мимо хоста его не получить.

### Пачкой

```cpp
using hook_request = graft_hook_request;   // { target, detour, original }

bool hook_all(std::span<const hook_request> all);
bool hook_all(std::initializer_list<hook_request> all);
template <class F> hook_request hooked(F target, F detour, F* original);
```

```cpp
graft::hook_all({graft::hooked(&Engine_Foo, &my_foo, &g_foo),
                 graft::hooked(&Engine_Bar, &my_bar, &g_bar)});
```

Пачка встаёт **целиком либо не встаёт вовсе**: половина врезок — это состояние, в котором
мод уже сломан, но ещё считает себя живым. Создание разбирает пролог и строит трамплин,
ничего не трогая; патч идёт вторым проходом, и если хоть одна заявка не создалась, до
патча дело не доходит.

Дешевле поштучной установки пачка **не становится**: сама врезка стоит сотые доли
миллисекунды (`Hook.InstallCostIsMeasured`).

### Когда врезка безопасна

Контракт один, и он не пожелание: **врезку ставят из точки входа плагина**. Не с тика, не
по событию в игре, не по команде из скрипта.

Причина в том, как патчится пролог. Переписываются первые байты функции, а внутри них есть
границы инструкций. Поток, снятый планировщиком ровно на такой границе, после пробуждения
продолжит с середины уже другой инструкции: сбоя у него нет, он спит, и ловушка safetyhook
на правах страницы его не видит. На стресс-кейсе это выглядит так:

```
[СБОЙ] code=C000001D rip=...51F1 ... answer=...51F0
```

Недопустимая инструкция, `rip` на один байт внутри цели.

Закрыть это можно только остановкой всех потоков процесса на время патча. В graft такой
остановки нет и не будет: `SuspendThread` останавливает поток внутри любого замка, включая
кучный, а под остановкой нужен именно он — взаимная блокировка неустранима, и цена ей
вечно висящий сервер вместо редкого падения. Вдобавок этот вызов в игровом процессе
выглядит ровно так, как выглядит вмешательство в чужую память, и в дереве его нет ни
одного.

Вместо остановки — условие, при котором гонки **не существует**, и graft ему удовлетворяет
устройством, а не дисциплиной. `hid.dll` тянется таблицей импорта exe до `main()`. В
`DllMain` заводится поток, он делает скан, ставит свои врезки и тут же зовёт точки входа
всех плагинов. Движок к этому моменту не создал ещё ни одного своего потока.

**Оговорка для плагина.** Своего крючка на этот момент у плагина пока нет. Статическая
инициализация плагина — и блоки `GRAFT_BINDINGS` вместе с ней — идёт раньше, чем хост
представится, и `graft::hook` там честно откажет: сервис врезки приезжает только в
`graft_plugin_entry`. Следующий раз C++ плагина просыпается на тике или в нативе, когда
потоки движка уже живы. Поэтому сейчас врезку ставят с первого тика (`GRAFT_ON_TICK`), и
безопасно это для функций, которые исполняет только игровой поток: тик идёт на нём же, и
пока он идёт, в цель никто другой не зайдёт. Функцию, которую зовут и другие потоки
движка, так перехватывать нельзя — это ровно гонка из примера выше.

**Снятая врезка не разрушается, а уходит в отставку.** Патч переводит поток, стоявший
внутри пролога, в трамплин — это делает сам safetyhook. Освободить трамплин сразу после
снятия значит убрать память из-под того, кто в ней исполняется. Трамплины снятых врезок
живут до конца процесса: десятки байт на снятие, а снимают редко.

**Снятая врезка не оставляет за собой ничего, что съест чужой сбой потом.** В апстриме
оставляла: список отравленных страниц там не чистится, а обработчик решает по признаку
«страница когда-то была нашей», и настоящий сбой на ней уходил в вечный повтор вместо
падения с дампом. Правится заплаткой на этапе конфигурации, см.
[SRC/patches/README.md](../SRC/patches/README.md): признак заменён на проверяемый — пока
окно патча открыто, всё как в апстриме, а после закрытия «продолжай» отвечается, только
если права страницы подтверждают, что повтор пройдёт. Сторожит кейс
`Hook.RemovedHookLeavesNothingThatSwallowsFaults`.

**Детур можно защитить так же, как натив:**

```cpp
graft::hook<&my_foo>(&Engine_Foo, &g_orig);   // падение в детуре отменит вызов, не игру
graft::hook_all({graft::hooked<&my_foo>(&Engine_Foo, &g_orig)});   // то же пачкой
graft::hook(&Engine_Foo, &my_foo, &g_orig);   // как было, под свою ответственность
```

Голая форма оставлена намеренно: детур, который обязан досылать управление оригиналу при
любом исходе, раскрутку пережить не может, и решать это вправе только его автор.

### Чего делать нельзя

> **Не вешайте хук на функцию, которую зовут из сотен мест с разными аргументами.**
> Детур на C++ считает регистры `xmm` своими, и чужой вызов с вещественным аргументом
> уезжает в движок испорченным. Это стоило трёх падений сервера. Если место вызова
> известно — перенаправляйте **его**, а не функцию: так сделан кадр
> ([`SRC/graft/frame.cpp`](../SRC/graft/frame.cpp), разбор — у `scan::frame_entry`).

Врезки — работа старта, а не игрового цикла: так велит контракт (см. выше), хотя сама по
себе она стоит сотые доли миллисекунды, а вызов после неё — один `jmp`.

## Объектный граф: `world.hpp`

```cpp
template <script_class T> vector position(T entity);
template <script_class T> std::expected<vector, miss> try_position(T entity);
```

Позиция сущности мира — движковый `IEntity.GetOrigin()`. Он есть у любой сущности:
объявлен на базовом классе, а поиск метода идёт с обходом базовых. Скриптовый
`Object.GetPosition()` отдаёт то же значение (сверяется в игре, кейс
`Entity_MethodsFromCpp`).

```cpp
const graft::vector at = graft::position(player);
```

Без движка — нули у `position` и промах в типе у `try_position`, но не падение.

Рядом в том же заголовке: `game()` — корень объектного графа, `spawn<T>()` — движковый
`typename.Spawn`, `borrowed<T>` — чужой объект с проверкой, что по адресу всё ещё объект
того же класса, `try_script_var` — переменная по имени руками движка.

## Сквозной пример

Так устроен реальный плагин: от имени класса до вызова метода, без единого зашитого
адреса.

```cpp
#include "graft/native.hpp"
#include "graft/scan.hpp"

namespace {

// Окна — числа вызывающего, и у каждого своя причина (здесь — по листингу метода в IDA).
constexpr std::size_t kThunk = 0x20;   // переходник слота: `jmp rel32` и ничего больше
constexpr std::size_t kBody  = 0x140;  // сколько тела метода разбираем; дальше — уже сосед

bool resolve() {
    const auto& sections = graft::scan::image();

    // 1. Класс -> его таблица. В настоящем плагине причину отказа пишут в журнал.
    const auto vt = graft::scan::rtti_vtable(".?AVAIBehaviourGoToTarget@@");
    if (!vt || graft::scan::vtable_slots(reinterpret_cast<void* const*>(*vt)) <= 10) {
        return false;
    }

    // 2. Виртуальный метод -> его тело. У слота бывает переходник, поэтому берём цель
    //    хвостового jmp, а не сам слот.
    std::uintptr_t entry = 0;
    std::memcpy(&entry, reinterpret_cast<const void*>(*vt + 10 * 8), sizeof entry);

    for (std::uintptr_t body : graft::scan::rel32_targets(sections, entry, kThunk, 0xE9)) {
        // 3. Сверка: кандидат становится ответом только когда совпал пролог.
        if (!graft::scan::matches(body, graft::scan::sig<"48 89 5C 24 10 57 48 83 EC 20">)) {
            continue;
        }
        // 4. Его собственные вызовы — то, ради чего всё и затевалось.
        for (std::uintptr_t callee : graft::scan::rel32_targets(sections, body, kBody)) {
            ...
        }
        return true;
    }
    return false;
}

}  // namespace
```

Дальше найденное либо зовётся (`scan::member_call<R>(fn, self, args...)` для метода
класса, обычный `reinterpret_cast` к `__fastcall` — для свободной функции), либо
перехватывается (`graft::hook`). Результат поиска мемоизируйте: он не меняется за жизнь
процесса.

## Цена

Замеры печатает сама сьюта (`graft_tests.exe`), поэтому числа не устаревают молча.

| Что | Цена | Когда платится |
|---|---|---|
| вызов после врезки | один `jmp` | — |
| установка врезки со снятием | ~0.02 мс (`Hook.InstallCostIsMeasured`) | старт |
| пачка | столько же на каждую врезку: пачка — ради «целиком или никак», не ради цены | старт |
| `rtti_vtable` на образе игры | ~3 мс (~20 ГБ/с × 61 МБ данных) | один раз, мемоизируйте |
| `matches`, `find_in_function`, `rel32_targets` на одной функции | наносекунды | разбор функции |
| `member_call`, `position` | как обычный вызов натива | — |

Ничего из этого не место на горячем пути. Разбор — на старте (или лениво, но один раз),
дальше в руках уже готовые адреса.
