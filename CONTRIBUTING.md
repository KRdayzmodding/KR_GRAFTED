# Как участвовать

GRAFT — прививка C++ к движку Enfusion. Здесь нет обрядов ради обрядов: правила ниже
существуют потому, что без них ломается либо сборка у тебя, либо чужие плагины в игре.

Коротко: **тест вперёд кода**, форматирование по `.clang-format`, коммиты Conventional
Commits, один PR — одна мысль. Всё остальное — подробности.

## 1. Окружение

Проект собирается **только под Windows** и **только clang-cl**: хост — это `dwmapi.dll`
рядом с exe игры, а плагины линкуются статическим рантаймом MSVC.

| Что | Версия | Откуда |
|---|---|---|
| Visual Studio 2022 или новее | Build Tools достаточно | компонент **Desktop development with C++** — из него берутся Windows SDK и STL |
| LLVM / clang-cl | **17+** (в проекте C++26 через `/clang:-std=c++2c`) | компонент VS **C++ Clang tools for Windows** или отдельный [LLVM](https://github.com/llvm/llvm-project/releases) |
| CMake | **3.30+** | из VS или отдельно |
| Ninja | любая | из VS или отдельно |
| clang-format | из того же LLVM | им проверяются изменённые строки в CI |

**Собирать нужно из «x64 Native Tools Command Prompt for VS 2022»** (или Developer
PowerShell). Это не придирка: clang-cl берёт пути к SDK и STL из переменных окружения,
которые ставит именно этот шелл. Из обычного `cmd` конфигурация упадёт на поиске
`windows.h`, и виноват будет не CMake.

Проверка, что всё встало:

```bat
cmake --preset release
cmake --build --preset release
cmake --build --preset tests
ctest --preset release
```

Четыре зелёные команды — окружение готово.

**Личных путей в репозитории нет.** Каталог игры, сервера и прочее своё держи в
`CMakeUserPresets.json` — он в `.gitignore`, это штатный механизм CMake:

```json
{
  "version": 6,
  "configurePresets": [
    { "name": "local", "inherits": "release",
      "cacheVariables": { "GRAFT_GAME_DIR": "C:/DayZServer" } }
  ]
}
```

Дальше вместо `--preset release` пишешь `--preset local`. PR, который приносит чужие пути в
`CMakePresets.json`, не принимается.

**VS Code:** в репозитории лежат готовые `.vscode/tasks.json` и `launch.json` — сборка,
тесты, примеры и отладка `graft_tests.exe` и `graft.exe doctor`. Окружение VS они
поднимают сами через `.vscode/dev-shell.cmd` (находит установку через `vswhere` и зовёт
`vcvars64.bat`), поэтому запускать VS Code из Developer-консоли не нужно. Отладка
требует расширения `ms-vscode.cpptools`.

IDE: `compile_commands.json` печатается в каталог сборки, `.clangd` в корне на него уже
настроен — VS Code, Neovim и CLion подхватывают без плясок.

### Что нужно только для скриптовой сьюты

Для правок в C++ игра не нужна вовсе — юнит-тесты гоняются без неё. Игра нужна, если
трогаешь то, что исполняется **внутри** движка (трамплины, вызов в другую сторону,
журналы): DayZ Diag и собранный мод тестов. Чужих модов не требуется — фреймворк uTest
лежит в репозитории файлом `tests/mod/SIXW_GRAFT/scripts/3_Game/uTest.c`, запуск —
`-scrDef=UTESTS_RUN -utest=seraph::graft`. Подробности — [tests/README.md](tests/README.md).

Если такой возможности нет — так и напиши в PR. Скриптовую часть прогонит мейнтейнер;
это не повод не присылать патч.

### Работа над graft прямо из своего мода

Самый частый путь сюда — «делал мод и упёрся в граблю в graft». Заводить ради неё
отдельный проект не нужно: `graft_import` умеет подключать локальный клон вместо
скачанного, и тогда graft становится обычной подпапкой твоей сборки.

```bat
git clone https://github.com/<ты>/KR_GRAFTED C:/src/graft
cd <твой мод>
cmake -B build -DGRAFT_SOURCE_DIR=C:/src/graft
```

С этого момента `graft_import` не качает ничего, а зовёт `add_subdirectory` на твой
клон (`cmake/graft.boot.cmake`): исходники graft видны в IDE рядом с модом, правка
применяется обычной пересборкой мода, и проверяется она сразу тем самым сценарием, из-за
которого ты и полез. Юнит-тесты гоняются в клоне обычным порядком — `cmake --preset
release` и дальше по разделу 2.

Готово — коммитишь и пушишь **из клона**, PR отправляешь оттуда же:

```bat
cd C:/src/graft
git switch -c fix/<тема>
git commit -am "fix(...): ..."
git push -u origin fix/<тема>
```

Обратно на скачиваемую версию — просто убрать `-DGRAFT_SOURCE_DIR` (или задать пустым)
и пересконфигурировать.

## 2. Тесты вперёд кода

Это главное правило проекта, и оно не про идеологию, а про то, что у половины
библиотеки цена ошибки — падение чужого сервера с игроками.

### Цикл

1. **Красный.** Сначала кейс, который падает и описывает желаемое поведение. Для бага —
   кейс, воспроизводящий баг: он обязан упасть на текущем коде, иначе он ничего не
   стережёт.
2. **Зелёный.** Минимальный код, от которого кейс проходит.
3. **Рефактор.** Чистка при зелёной сьюте.

В PR это видно по истории: сначала коммит с падающим тестом или тест и реализация в одном
коммите — но никогда не «реализация сейчас, тесты потом». «Потом» не наступает.

### Куда какой тест

| Что проверяешь | Куда | Чем гоняешь |
|---|---|---|
| разбор, генерация, типы, логика загрузчика, сканер | `tests/*_test.cpp` (gtest) | `cmake --build --preset tests` + `ctest --preset release` |
| поведение натива по эту сторону границы | `tests/plugins/natives.cpp` + кейс сьюты | сьюта в игре |
| то, что исполняет сам движок: трамплины, маршалинг, вызов в другую сторону, журналы | `tests/mod/SIXW_GRAFT/scripts/3_Game/seraph_graft_test.c` | `run_suites(["seraph::graft"])` |

Правило выбора простое: **если это можно проверить без игры — оно обязано проверяться без
игры.** `callout_test` гоняет вызов движковых `proto` против фальшивого движка — дескриптор
и его параметры разложены руками по `graft::layout`. Так же поступай и ты: подделать
движок дешевле, чем каждый раз запускать DayZ.

Что подделать нельзя — идёт в скриптовую сьюту. Это не запасной аэродром, а второй
обязательный уровень: 88 кейсов там ловят ровно то, чего llvm-cov не видит в принципе.

### Покрытие

```bat
cmake --preset debug -DGRAFT_COVERAGE=ON
cmake --build --preset coverage
```

**73.7% по строкам — это потолок оффлайнового измерения, а не лень.** Трамплины
(`marshal.hpp`, `dispatch.hpp`) зовёт движок, `script_host.cpp` требует его указателей.
Гнаться за цифрой, дописывая тесты ради строк, не надо: за этими файлами стоит сьюта.
Падение покрытия в тех файлах, что покрываются оффлайн, — повод для вопроса в ревью.

### Скорость

`Perf_HotPathBudget` — вентиль цены вызова. Он меряет **отношение** к ванильному
`map.Count()`, а не миллисекунды, потому что миллисекунды на живой игре плавают на ±30%.
Тронул горячий путь (трамплин, маршалинг, guard) — прогоняй его и приложи числа к PR.

## 3. Ветки, коммиты, PR

**Ветки.** `main` — стабильная и защищённая, прямой push в неё запрещён. Работа — в
ветках от `main`:

```
feat/<тема>      новое
fix/<тема>       починка
docs/<тема>      документация
test/<тема>      только тесты
refactor/<тема>  без смены поведения
```

**Долгоживущих веток в проекте нет — только `main`.** Ни `dev`, ни `develop`, ни
`release/*`: каждая ветка рождается под одну задачу, живёт до мержа и удаляется. Целевая
ветка любого PR — `main`, других вариантов нет.

Это решение с ценой и с причиной. Цена: работу приходится резать на куски, каждый из
которых сам по себе не ломает библиотеку. Причина: ветка, живущая параллельно `main`,
копит конфликты ровно с той скоростью, с какой её не сливают, а когда её перестают
кормить — не исчезает, а молча собирает PR-ы, которые уже некуда влить.

Если работа не режется — не заводи ветку-долгожителя, а разбей задачу: сначала PR с
инфраструктурой и тестами, которые проходят на старом поведении, потом PR с переключением.
Так каждый шаг проверяем и обратим.

**Коммиты** — [Conventional Commits](https://www.conventionalcommits.org/ru/):

```
feat(loader): плагин может объявить зависимость от другого
fix(scan): якорь не находился на сборке 1.30
test(callout): формы вызова у методов типа-значения
```

Область (`loader`, `scan`, `marshal`, `build`, `docs`…) — по месту правки. Язык описания —
русский или английский, единообразно внутри одного PR.

**PR.** Один PR — одна мысль. Заголовок PR становится текстом squash-коммита, поэтому
пиши его как коммит. Дальше — чеклист из шаблона; он короткий и весь по делу.

Мержится только **squash**, история линейная. Ветку после мержа GitHub удалит сам.

**Первый PR** потребует подписать [CLA](docs/CLA.md) — бот сам оставит комментарий и
скажет, что ответить. Один раз на все будущие PR.

## 4. Что не примут

- **Зашитые адреса и RVA в коде библиотеки.** Точки движка ищутся в рантайме по именам
  ванильных нативов (`INCLUDE/graft/scan.hpp`). Это принцип, а не деталь реализации:
  ровно поэтому патч игры двигает адреса, а не ломает прививку.
- **Код, скопированный из движка** — исходный или восстановленный декомпилятором.
  См. раздел 6.
- **Правки `grafted_natives_*.c` руками.** Это артефакт генератора, как `.pb.cc` у
  protobuf. Разъехаться с C++ он не может, потому что его печатает сборка.
- **Чужие пути** в `CMakePresets.json`, личные каталоги, `P:\` и прочее машинное.
- **`git submodule` на приватные репозитории.** Публичное обязано собираться само.
- **Новая логика без теста.** См. раздел 2.
- **Форматирование всего файла заодно.** Диффы «поправил стиль во всём файле + одна
  строка по делу» невозможно ревьюить. Форматируй то, что тронул.
- **Смена `GRAFT_ABI_VERSION` мимоходом.** См. раздел 5.

## 5. ABI: почему это отдельная церемония

Плагины собираются **отдельно от хоста** и приезжают к людям готовыми DLL. Хост при
загрузке сверяет числа и отклоняет всё, что не совпало
(`SRC/graft/plugins.cpp`, проверка `info.abi != GRAFT_ABI_VERSION`). Значит бамп числа в
`INCLUDE/graft/abi.h` разом убивает **все чужие плагины в природе** — их придётся
пересобрать.

Поэтому:

| Число | Когда меняется | Что обязано случиться вместе с ним |
|---|---|---|
| `GRAFT_ABI_VERSION` | изменился интерфейс хост↔плагин | минорная версия graft, метка `abi-break` на PR, запись в `CHANGELOG.md`, абзац «пересоберите плагины» в release notes |
| `GRAFT_LAYOUT_VERSION` | переехали структуры **движка** (новая сборка игры) | запись в `CHANGELOG.md`; это не «мы поменяли API», это «игра поменялась» |

CI это стережёт: если diff трогает `INCLUDE/graft/abi.h`, а `CHANGELOG.md` — нет, джоба
`abi` падает.

**Граница публичного API**: публичны заголовки `INCLUDE/graft/`, которые тянет
`graft/native.hpp`. Всё остальное — внутреннее и может поменяться в любой версии без
предупреждения. Если твоя правка меняет сигнатуру публичного — скажи об этом в PR прямым
текстом.

## 6. RESEARCH/ — где проходит граница

[RESEARCH/](RESEARCH/) — это база знаний о движке и скрипты, которыми она добыта.
Граница проходит между **фактом** и **копией**:

**Можно:**

- факты, изложенные своими словами: адреса и RVA с указанием сборки игры, раскладки
  структур, биты флагов, формы вызова;
- короткие иллюстративные фрагменты дизассемблера и псевдокода — несколько строк,
  аннотированных собственным разбором, там, где без них объяснение разваливается;
- IDAPython-скрипты, которыми находка перепроверяется.

**Нельзя:**

- бинарь игры и любые его части, распакованные игровые файлы, ванильные скрипты;
- базы IDA (`.i64`), содержимое `RESEARCH/out/` — то есть **дампы** вывода
  декомпилятора и дизассемблера. Эти каталоги в `.gitignore`, и оттуда их не вынимать.

**Каждая находка подписывается сборкой игры и снабжается скриптом, которым
перепроверяется.** Вывод без скрипта — не находка, а слух: после патча игры проверить
его будет нечем. Шаблон issue `research_finding` спрашивает ровно это.

## 7. Лицензия вклада

Проект под **GPL-3.0-or-later** с **GRAFT plugin exception 1.0**. Присылая PR, ты
отдаёшь вклад на тех же условиях и разрешаешь правообладателю лицензировать его и иначе —
подробности и подпись в [docs/CLA.md](docs/CLA.md).

Отдельно из CLA, пункт 5.4: **во вкладе не должно быть кода, восстановленного из
проприетарного бинаря.** Это то же правило, что в разделе 6, но с твоей подписью.

## 8. AI-ассистенты

Работу, сделанную с языковой моделью, принимаем — при одном условии: **ответственность за
неё твоя целиком, и ты понимаешь каждую строку, которую прислал.** Ревью исходит из того,
что автор PR может объяснить любое место в нём.

Что закроет PR без разговора:

- **выдуманные факты про движок.** Модель охотно сочиняет смещения, имена нативов и
  поведение интерпретатора — уверенно и правдоподобно. Находка, добытая беседой с
  ассистентом, а не скриптом из `RESEARCH/scripts/`, — не находка (раздел 6);
- **тесты, написанные под реализацию.** Кейс, который утверждает ровно то, что код и так
  делает, не стережёт ничего. Тест пишется от требования и обязан падать до правки
  (раздел 2);
- **следы ассистента в тексте**: «Надеюсь, это поможет», «Дайте знать, если нужны
  правки», пересказ кода в комментариях, объяснение очевидного на три абзаца, страницы
  сплошных булитов;
- **чужой код без происхождения.** Модель может выдать заимствование под несовместимой
  лицензией и не сказать об этом. Проверить — твоя обязанность, и ты подписываешь это в
  CLA (пункт 5.3), а для кода из декомпилятора — в пункте 5.4.

Коротко: ассистент — инструмент, а не соавтор, на которого можно сослаться.
